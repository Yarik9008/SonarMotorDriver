# Релизные образы прошивок (Intel HEX)

Готовые образы для прошивки **STM32F103C8** (адрес загрузки `0x08000000`).
Оба файла получены из `firmware.elf` соответствующей сборки командой
`arm-none-eabi-objcopy -O ihex` (см. [Сборка](#сборка)) — обратное преобразование
образа в binary даёт файл, побайтно равный `firmware.bin` из `.pio/build/`.

| Файл | Описание | Flash (по отчёту `pio run`) | RAM |
| ---- | -------- | --------------------------- | --- |
| `FW_SonarMotorDriver.hex` | Основная прошивка (`pio run -e hw`): PID, BiSS C (LENZ IRS), TMC2209, командный UART, скан сектора, синхронизация SYNC_OUT/SYNC_IN (`sync=`), режим выдачи телеметрии `om=`, снятие удержания вала `hold=`, запросы состояния `om`/`hold` | 48 544 B (74.1%) | 3 604 B (17.6%) |
| `FW_SonarMotorDriver_Sim.hex` | Имитатор (`pio run -e sim`): **та же прошивка** с виртуальными энкодером и мотором вместо BiSS C и TMC2209 — вся логика (PID, профиль движения, скан, синхронизация, телеметрия) общая с основным образом | 40 404 B (61.7%) | 2 904 B (14.2%) |

Проценты и байты — из вывода `pio run` (секции `.text` + `.rodata` + `.data`).
Фактический объём, который образ занимает во флеше (вместе с таблицей векторов
`.isr_vector` и массивами `.init_array`/`.fini_array`), — 48 824 B у основной
прошивки и 40 684 B у имитатора.

## Что нового в этих образах

**Имитатор перестал быть отдельной прошивкой.** Раньше это был самостоятельный
проект со своей копией логики — и копии успели разойтись: например, сектор
скана через ноль (`scan=350,10,5,100`) основная прошивка принимала, а имитатор
отвечал `err:scan`. Теперь оба образа собираются из одного проекта
[`Software/FW_SonarMotorDriver`](../Software/FW_SonarMotorDriver/README.md)
двумя окружениями PlatformIO, и различает их ровно одно — какой слой железа
попал в сборку:

- `pio run -e hw` — `src/biss_c.c` (энкодер BiSS C) и библиотека `lib/tmc2209`;
- `pio run -e sim` — `src/sim_backend.c`: виртуальный энкодер и виртуальный
  шаговый двигатель.

Условий компиляции внутри логики нет: `main.c` в обеих сборках один и тот же
файл, поэтому имитатор считает настоящий ПИД, отрабатывает тот же профиль
скорости и ускорения и обслуживает команды тем же кодом. Разойтись в поведении
им больше нечем. Образ имитатора из-за этого вырос (34 632 → 40 404 B): в нём
теперь вся логика прошивки, а не её упрощённое повторение.

Помимо синхронизации со внешним триггером (`sync=0/1/2`, запрос `sync`) оба
образа содержат две команды протокола, которых не было в предыдущем релизе:

- **`om=0/1/2`** — источник выдачи телеметрии: по таймеру `op=` / по приходу
  в целевую позицию (кадр помечается `,ev:1`) / оба сразу. Позволяет получать
  ровно один кадр на точку скана вместо непрерывного потока.
- **`hold=0/1`** — снятие и возврат удержания вала. При `hold=0` обмотки
  обесточиваются (тихая пауза на замер), цель и точка скана сохраняются, отсчёт
  паузы скана заморожен; `hold=1` возвращает ток и вал садится в ту же точку.
  В имитаторе удержание воспроизводится протокольно: модель движения встаёт
  на паузу.

Кроме того, в оба образа добавлены **запросы состояния `om` и `hold`** —
ключевое слово без `=`. Ответ — одна строка `om=<0..2>` / `hold=<0|1>` **без
префикса `ok:`**, как у существующего запроса `sync`. Нужны хосту после
подключения: плата могла перезагрузиться или работать с другим хостом, а для
`hold` это ещё и вопрос безопасности (обесточенный вал с виду не отличается от
стоящего под током). Команды установки не изменились: `om=1` по-прежнему
отвечает `ok:om=1`, `hold=0` — `ok:hold=0`. Обработчики и парсер у прошивок
общие, поэтому строки ответов в основной прошивке и имитаторе совпадают.
Основная прошивка выросла от этих двух команд ровно на 80 байт
(48 464 → 48 544), и это целиком код: новых строковых литералов в образе не
появилось — форматы
`om=%u\r\n` и `hold=%u\r\n` компоновщик взял хвостами уже имевшихся
`ok:om=%u\r\n` и `ok:hold=%u\r\n`.

Формулировать это через «сколько раз встречается» нельзя: значение имеет не
число вхождений, а то, начинает ли вхождение отдельную строку. В `.rodata`
строки лежат подряд через завершающий ноль, и новый литерал выдал бы себя нулём
прямо перед собой. Такого нет ни одного. При этом сами вхождения считаются
по-разному: `om=%u\r\n` встречается в образе один раз (внутри
`ok:om=%u\r\n`), а `hold=%u\r\n` — **два** раза, потому что он оказался
хвостом сразу двух строк: `ok:hold=%u\r\n` и `ok:ihold=%u\r\n` (команда
`ihold` была в прошивке и раньше). Оба вхождения `hold=%u\r\n` — хвосты,
отдельной строки среди них нет.

Проверка на любом из двух образов — скрипт в шесть строк:

```python
# check_literals.py — не начинает ли формат отдельную строку в .rodata
import re, sys
b = open(sys.argv[1], 'rb').read()
for pat in (b'om=%u\r\n', b'hold=%u\r\n'):
    for m in re.finditer(re.escape(pat), b):
        s = b.rfind(b'\x00', 0, m.start()) + 1   # начало строки в .rodata
        print(f'{m.start():#x}',
              'ОТДЕЛЬНАЯ СТРОКА' if s == m.start() else 'хвост',
              repr(b[s:m.end()]))
```

```bash
python check_literals.py \
  Software/FW_SonarMotorDriver/.pio/build/hw/firmware.bin
```

Вывод для `FW_SonarMotorDriver` — слова «ОТДЕЛЬНАЯ СТРОКА» в нём быть не должно:

```
0xb4ab хвост b'ok:om=%u\r\n'
0xb597 хвост b'ok:ihold=%u\r\n'
0xb641 хвост b'ok:hold=%u\r\n'
```

У имитатора картина та же, смещения `0x96a7`, `0x9793`, `0x983d`.

Там же исправлена **верхняя граница аргумента `mstep`**: парсер проверяет
`0…65535` до приведения к `uint16_t`, поэтому `mstep 65537` теперь отбрасывается
молча, а не превращается в `ok:mstep=1` с переключением драйвера на полный шаг.
Проверка добавлена только сверху — ответы на значения `0…65535` прежние.

Полное описание протокола — [Docs/Protocol.md](../Docs/Protocol.md), шпаргалка —
[Docs/Protocol_QuickStart.md](../Docs/Protocol_QuickStart.md), стыковка с внешним
оборудованием — [Docs/Sync.md](../Docs/Sync.md).

## Что в этих образах не проверено на плате

Оба образа собраны и сверены с `firmware.bin` только на ПК. Основная прошивка
при этом байт в байт совпадает с образом прошлой сборки
(`5e8f33f4…`): объединение проектов её кода не коснулось — `main.c`, `board.h`
и библиотеки остались прежними, изменился только состав сборки имитатора.
Поэтому весь непроверенный на плате остаток — это имитатор, и он сменился
целиком.

- **Имитатор собран из логики основной прошивки.** Прежняя отдельная прошивка
  повторяла её вручную; теперь это тот же `main.c` с виртуальным энкодером и
  виртуальным мотором (`src/sim_backend.c`). На плате, прошитой имитатором,
  этот образ не запускался ни разу. Что стоит проверить первым: выход в «дом»
  после сброса (вал модели стартует с 37.5° и идёт в 0°), приход в точку скана
  и кадр `ev:1`, поведение `hold=0/1`.
- **Командный UART имитатора тоже сменился**: он собран с
  [`lib/sonar_proto`](../Software/FW_SonarMotorDriver/lib/sonar_proto/README.md)
  прошивки и получил
  три исправления, которых не было в его прежней копии (удержание участка
  TX-кольца до конца передачи, снятие RXNE у ещё не готового USART3, разбор
  ошибок линии в `HAL_UART_ErrorCallback`). На железе этот код проверялся
  только в составе основной прошивки.
- **USART3 у имитатора теперь работает как у основной прошивки** — на
  прерываниях, а не на DMA: `board.h` общий, `UART3_USE_DMA` = 0. Прежний
  имитатор использовал DMA, потому что каналы DMA1 у него были свободны.
- **Boot-баннер имитатора** (`boot:rst=… fw=1.0.0-sim`) и **дублирование TX на
  USART3** видны только в собранном образе и в исходниках — на живой линии их
  никто не наблюдал.
- Соответствие протоколу проверяется на ПК Python-моделью прошивки
  (`Software/SonarDebugGUI/protocol_test.py --sim`), а она воспроизводит
  **строки** протокола, а не реальный UART: тайминги, переполнение колец,
  ошибки линии и поведение DMA в ней не моделируются.

Первое включение любого из этих образов на плате следует считать отладочным.

## Сборка

Оба образа собираются из одного проекта — окружениями `hw` и `sim`:

```bash
cd Software/FW_SonarMotorDriver && pio run -e hw -e sim
```

PlatformIO для этой платы собирает `firmware.elf` и `firmware.bin`, но **не**
`firmware.hex` — Intel HEX делается из ELF вручную. Пути ниже даны от корня
репозитория; `arm-none-eabi-objcopy` в PATH обычно нет — он лежит в пакете
PlatformIO `~/.platformio/packages/toolchain-gccarmnoneeabi/bin/`:

```bash
arm-none-eabi-objcopy -O ihex \
  Software/FW_SonarMotorDriver/.pio/build/hw/firmware.elf \
  Release/FW_SonarMotorDriver.hex

arm-none-eabi-objcopy -O ihex \
  Software/FW_SonarMotorDriver/.pio/build/sim/firmware.elf \
  Release/FW_SonarMotorDriver_Sim.hex
```

Под Windows `objcopy` пишет строки с CRLF, а в репозитории Intel HEX хранится
с LF (`*.hex text eol=lf` в [.gitattributes](../.gitattributes)), поэтому после
генерации переводы строк нормализуются — иначе SHA256 файла в рабочем дереве не
совпадёт с тем, что получит `git clone`:

```bash
sed -i 's/\r$//' Release/*.hex   # Git Bash / любой POSIX-шелл
```

Проверка образа без платы — обратное преобразование и сравнение с `firmware.bin`
(переводы строк в HEX на результат не влияют):

```bash
arm-none-eabi-objcopy -I ihex -O binary Release/FW_SonarMotorDriver.hex check.bin
cmp check.bin Software/FW_SonarMotorDriver/.pio/build/hw/firmware.bin
```

## Прошивка

> Требуется плата и программатор — команды этого раздела на ПК не проверяются.

Штатный путь (PlatformIO берёт **`firmware.bin`** из `.pio/build/`, а не файл
из `Release/`; `openocd` подставляется из пакета `tool-openocd`):

```bash
cd Software/FW_SonarMotorDriver
pio run -e hw --target upload    # или -e sim для имитатора
```

Прошивка готовым образом из `Release/` — тем же адаптером WCH-Link
(CMSIS-DAP/SWD), из корня репозитория. Адрес в команде не указывается: он есть
в самом Intel HEX. `openocd` в PATH может не быть — тогда берите бинарник из
пакета PlatformIO (`~/.platformio/packages/tool-openocd/bin/openocd`):

```bash
openocd -f Software/FW_SonarMotorDriver/openocd/wch-link.cfg -f target/stm32f1x.cfg \
  -c "program Release/FW_SonarMotorDriver.hex verify reset" \
  -c "shutdown"
```
