# Протокол взаимодействия с платой SonarMotorDriver

Полное описание текстового UART-протокола, которым хост (ПК, ROS-узел, GUI)
управляет платой SonarMotorDriver и получает от неё телеметрию. Протокол
идентичен для [основной прошивки](../Software/FW_SonarMotorDriver/) и её
[имитатора](../Software/FW_SonarMotorDriver_Sim/) — по линии связи они
неотличимы (расхождения см. в разделе [«Основная прошивка и имитатор»](#основная-прошивка-и-имитатор)).
Готовая эталонная реализация клиента — [SonarDebugGUI](../Software/SonarDebugGUI/)
(`sonar_gui/protocol.py`, `sonar_gui/controller.py`).

> **Нужно быстро?** Шпаргалка на одну страницу — [Protocol_QuickStart.md](Protocol_QuickStart.md):
> подключение, все команды одной таблицей, телеметрия, типовые сценарии.

## Физический транспорт

| Параметр       | Значение                                                             |
| -------------- | --------------------------------------------------------------------- |
| Интерфейс      | UART, 8N1, **115200 бод**, без аппаратного управления потоком         |
| Основной порт  | **USART1**: PA9 = TX (плата → хост), PA10 = RX (хост → плата)         |
| Разъём         | J2, Pin 4 = TX, Pin 3 = RX, GND — общий                                |
| Дублирующий порт | **USART3**: PB10 = TX, PB11 = RX — и в основной прошивке, и в имитаторе (см. ниже) |
| Уровни         | 3.3 В логика — для подключения к ПК нужен USB-UART переходник         |

**Дублирование на USART3.** Плата одновременно обслуживает два физических
UART-порта с полностью одинаковым протоколом:

- **TX дублируется** — каждая исходящая строка (ответ на команду, телеметрия,
  boot-баннер, `err:stall`) отправляется в оба порта одновременно и попадает
  в очередь только если место есть **в обоих**; если хотя бы один порт
  переполнен — сообщение не уходит ни в один (порты не расходятся друг с
  другом по потоку).
- **RX объединяется** — байты, принятые по USART1 и по USART3, сливаются в
  один общий приёмный буфер команд. Отправлять команды можно в любой из двух
  портов (или в оба сразу) — с точки зрения парсера это один поток.
- Типичное применение: USART1 — рабочий канал к хосту (или бутлоадер), USART3
  — параллельный отладочный/логирующий выход (например, к отдельному логгеру
  или второму ПК), не мешающий основному каналу.
- **Имитатор** ([FW_SonarMotorDriver_Sim](../Software/FW_SonarMotorDriver_Sim/))
  поднимает оба порта и дублирует TX точно так же: транспорт у прошивок
  общий (`Software/lib/sonar_proto/src/uart.c`), а выводы и скорости он
  берёт из своего `include/board.h` (`UART3_INSTANCE` = USART3, PB10/PB11,
  `UART_PORT_COUNT` = 2). Различие непротокольное: у имитатора USART3
  работает на DMA (`UART3_USE_DMA` = 1), у основной прошивки — на
  прерываниях (`UART3_USE_DMA` = 0: каналы DMA1 Ch2/Ch3 отданы SPI1
  энкодера). Скорость и формат кадра от этого не зависят.

**UART-бутлоадер.** Прошивку платы можно обновить и через штатный UART
bootloader STM32 (BOOT0 = 1 при сбросе, те же контакты PA9/PA10) —
см. `AN2606` в [Docs/Datasheet/](Datasheet/).

## Формат кадра

Протокол текстовый, построчный, без бинарных полей и контрольных сумм —
целостность обеспечивается только UART (parity отключена, ошибки кадрирования
на уровне протокола не детектируются).

- **Кодировка:** ASCII (без пробелов и unicode в значимых частях команд/ответов).
- **Разделитель строк:** плата принимает `\n`, `\r` и `\r\n` как конец строки —
  все три варианта равнозначны. Все ответы платы завершаются `\r\n`.
- **Пустые строки** (два подряд идущих разделителя, например от `\r\n\r\n`)
  молча пропускаются — ответа на них нет.
- **Максимальная длина строки команды — 63 символа** (буфер приёма 64 байта
  с завершающим `\0`). Более длинная команда без разделителя строки будет
  обрезана логикой защиты приёмного кольцевого буфера (128 байт) — старые
  байты вытесняются новыми, пока не появится разделитель; такую команду
  парсер, скорее всего, не распознает. На практике все штатные команды
  укладываются в 20–30 символов.
- **Регистр значим:** ключевые слова команд — только строчные буквы (`en`,
  не `EN`). Команда в другом регистре не распознаётся ни одним из шаблонов
  и трактуется как неизвестная (`err:unknown`).
- **Числа:** разбираются стандартными `strtof`/`strtol`, поэтому:
  - ведущие пробелы/табы после `=` или после обязательного пробела (в
    `irun`/`ihold`/`icur`/`mstep`) допустимы и пропускаются;
  - `inf`/`nan` (которые `strtof` в общем случае принимает) явно отклоняются
    парсером как недопустимые;
  - **строка не обязана заканчиваться сразу после числа** — хвостовые символы
    после успешно распознанного числа игнорируются. Например, `t=90xyz`
    будет принято как `t=90`. Это особенность парсера, а не гарантированное
    поведение — не полагайтесь на него, отправляйте только сам синтаксис
    команды.
- **Один ответ на одну команду**, синхронно и без подтверждения приёма на
  транспортном уровне (нет ACK/NACK, есть только текстовый `ok:`/`err:`).
  Присылать следующую команду до получения ответа на предыдущую не
  запрещено (парсер построчный и не блокирует приём), но так как строки
  никак не нумеруются, сопоставлять команды с ответами при таком
  «конвейере» на хосте сложнее — рекомендуется дожидаться ответа перед
  отправкой следующей команды (см. [«Практические рекомендации»](#практические-рекомендации-для-хоста)).

**Два класса ошибок разбора** — важно различать:

| Ситуация                                                                 | Реакция платы                                  |
| ------------------------------------------------------------------------- | ----------------------------------------------- |
| Команда целиком не распознана (опечатка, несуществующее слово, регистр)   | `err:unknown\r\n`                                |
| Команда распознана (совпал префикс, напр. `t=`), но аргумент не разобрать как число (например `t=abc`, `v=`, `mstep xyz`) **или** целое число не помещается в диапазон, который проверяет сам парсер (`op=70000`, `mstep 70000`, `hold=2`) | **Ответа нет вообще** — строка молча отбрасывается на этапе `Cmd_Parse`, `ProcessCommand` не вызывается |
| Команда и аргумент синтаксически корректны, но значение вне допустимого диапазона (например `v=99999`) | `err:bad arg ...\r\n` с указанием допустимого диапазона |

Второй случай — частая ловушка при отладке нового клиента: если на команду
нет вообще никакого ответа (не `err:...`, а тишина), проверьте в первую
очередь синтаксис числового аргумента.

## Модель взаимодействия

Обмен полудуплексный по смыслу (не по электрике): хост присылает **команды**,
плата на каждую распознанную команду присылает ровно одну строку **ответа**
(`ok:...` либо `err:...`; команды-запросы — `mcfg`, `sync`, `om`, `hold` — тоже
отвечают одной строкой, но состоянием, без префикса `ok:`, см. [«Запрос
состояния»](#запрос-состояния-om-hold)). Независимо от команд плата без запроса шлёт
строки **телеметрии**: по умолчанию — с фиксированным периодом, а по
команде `om=` — в момент прихода в заданную позицию (или и то, и другое)
— см. [«Режим выдачи (`om`)»](#режим-выдачи-om). Дополнительно
возможны **асинхронные** строки, не привязанные ни к одной конкретной
команде (boot-баннер, `err:stall`, отложенный результат `diag`) — см.
[«Асинхронные сообщения»](#асинхронные-несолиситированные-сообщения).

Состояние платы, релевантное протоколу:

- **Драйвер включён / выключен** (`en` / `dis`) — управляет только тем,
  подаётся ли ток на обмотки и активен ли контур регулирования; сама плата
  всегда готова принимать команды независимо от этого флага.
- **Режим closed-loop / open-loop** (`m: cl` / `ol` в телеметрии) — плата
  сама переключается в open-loop, если энкодер не отвечает дольше 500 мс, и
  возвращается в closed-loop, как только чтения энкодера восстановились.
  Хост не может переключить режим командой напрямую — только чинить
  причину (питание/кабель энкодера) и наблюдать за `ec`/`m`.
- **Тип движения** — один из четырёх взаимоисключающих режимов: покой
  (движение к статичной цели `t=X` или уже прибыл), непрерывное вращение
  (`t=+`/`t=-`), зигзаг-сканирование или бесконечное сканирование
  (`scan=...`). Любая новая команда движения (`t=`, `t=+/-`, `scan=`, `stop`)
  безусловно отменяет предыдущий тип движения.

## Загрузочная последовательность

После подачи питания или любого сброса плата проходит нижеследующие шаги
**без участия хоста**; часть шагов сопровождается строками, которые хост
увидит без всякого запроса:

1. Инициализация UART (до 3 попыток; при неудаче плата продолжает работать
   без командного канала — телеметрии и ответов не будет, LED мигает в
   5 раз чаще как индикация неисправности).
2. **Boot-баннер** — первая строка, которую плата отправляет:
   ```
   boot:rst=por fw=1.0.0
   ```
   `rst` — причина последнего сброса (см. таблицу ниже), `fw` — версия
   прошивки (`-DFW_VERSION` в `platformio.ini`, по умолчанию `dev`).
   Баннер шлют обе прошивки — и основная (`fw=1.0.0`), и имитатор
   (`fw=1.0.0-sim`, тот же код и тот же момент выдачи: сразу после подъёма
   UART, до строки `enc:ok`). Суффикс `-sim` в версии — единственный
   протокольный признак, по которому хост отличает имитатор.

   | Флаг   | Источник сброса                      |
   | ------ | -------------------------------------- |
   | `por`  | Power-on / brown-out reset             |
   | `pin`  | Внешний сброс по выводу NRST           |
   | `sft`  | Программный сброс (NVIC_SystemReset)   |
   | `iwdg` | Сработал независимый сторожевой таймер |
   | `wwdg` | Сработал оконный сторожевой таймер     |
   | `lpwr` | Выход из режима низкого энергопотребления (low-power) |
   | `-`    | Ни один флаг не установлен              |

   Частый `rst=iwdg` в логах — верный признак того, что плата зависает и
   перезапускается сторожевым таймером; полезно как первая диагностика при
   «плата не отвечает / не мигает».
3. Инициализация BiSS C (SPI1 + THVD1452), пауза `ENCODER_STARTUP_MS` = 50 мс
   на готовность энкодера после подачи питания.
4. **Стартовая диагностика энкодера** — 16 чтений с интервалом 2 мс между
   ними (~32 мс на серию). Критерии успеха те же, что и у команды `diag`
   (см. ниже) — отличается только момент запуска и темп чтений. По
   результату — одна из строк:
   ```
   enc:ok n=16/16 spread=0.012 pos=179.82
   err:enc n=8/16 spread=0.750 last=2
   ```
   Требование прохождения: ≥ 12 из 16 чтений валидны **и** разброс позиции
   ≤ 0.5°. Если диагностика провалена — мотор при старте не включается и
   автоматический выход в домашнюю позицию не выполняется (домашняя позиция
   привязывается к текущей, без движения); если позже энкодер восстановится
   сам, мотор всё равно останется управляемым только явными командами
   оператора.
5. Инициализация драйвера TMC2209. При ошибке — асинхронная строка
   `err:motor_init=<код>\r\n`.
6. Запуск таймера опроса 1 кГц и IWDG (таймаут ≈ 500 мс, при зависании
   main-цикла плата перезагрузится сама с `rst=iwdg` в следующем баннере).

После этого плата в рабочем состоянии: телеметрия идёт с настройками по
умолчанию (`om=0`, период 4 мс, `debug=0`), драйвер включён (`g_enabled = 1`) и, при
успешной диагностике, мотор автоматически перемещается в домашнюю позицию
(смещение от 0° задаётся `STARTUP_TARGET_OFFSET_DEG`, по умолчанию 0°).

## Команды

Все команды — однострочные ASCII-строки, см. правила разбора выше. Столбец
«Ответ» показывает формат при успехе; варианты ошибок — отдельно под
таблицей или в общем разделе про диапазоны.

### Включение/выключение и остановка

| Команда | Действие                                                                | Ответ      |
| ------- | ------------------------------------------------------------------------ | ---------- |
| `en`    | Включить драйвер и контур регулирования. Целью становится **текущая** позиция (плавный старт без рывка) | `ok:en`    |
| `dis`   | Выключить драйвер (обмотки обесточены). Любая ранее заданная командой `t=` цель отбрасывается | `ok:dis`   |
| `stop`  | Остановить любое движение (позиционирование, вращение, скан), не выключая драйвер | `ok:stop`  |

Для тихой паузы на время замера (обмотки обесточены, но цель и состояние
скана сохраняются) `dis` не годится — см. [«Удержание вала
(hold)»](#удержание-вала-hold).

> **`t=` при выключенном приводе.** Уставка, заданная командой `t=…`, пока
> драйвер выключен (`dis`), не сохраняется: следующая команда `en`
> безусловно привязывает цель к текущей позиции энкодера. Задавайте
> позицию командой `t=…` **после** `en`, а не до.

### Система координат

Координата **кольцевая, один оборот**: позиция, цель и точки скана всегда
лежат в диапазоне **[0, 360)**, накопителя оборотов нет. Из этого следует:

- Ход к цели идёт **всегда кратчайшим путём** (не более 180°). Задать
  «доехать на оборот дальше» нельзя — `t=370` эквивалентно `t=10`.
- При пересечении нуля координата заворачивается: `359.9°` → `0.1°`.
  В телеметрии `cp` никогда не выходит за `[0, 360)`.
- Поле `pe` — ошибка **по кратчайшему пути**, в диапазоне `(-180, 180]`:
  при `tp=10`, `cp=350` она равна `+20.00`, а не `-340.00`.
- Непрерывное вращение (`t=+`/`t=-`) и бесконечный скан этим **не
  ограничены** — вал крутится сколько угодно, в телеметрии видно текущий
  угол по кольцу.

### Позиционирование

| Команда  | Действие                             | Ответ            |
| -------- | -------------------------------------- | ---------------- |
| `t=180`  | Целевая позиция, градусы (float, знак и дробная часть допустимы) | `ok:t=180.00` |

Значение вне `[0, 360)` **приводится к диапазону**, а не отвергается:
`t=370` → `ok:t=10.00`, `t=-30` → `ok:t=330.00`, `t=720` → `ok:t=0.00`.

Ответ повторяет уставку в стандартизованном виде (`%.2f`), а не эхо
исходной строки — по нему удобно проверять, как именно плата разобрала
число (в т.ч. каким углом обернулось значение вне диапазона).

### Непрерывное вращение

Бесконечное вращение без привязки к конкретному углу, без ограничения по
PID — используется, например, для быстрой ручной подводки («джог»).

| Команда | Направление          | Ответ      |
| ------- | ---------------------- | ---------- |
| `t=+`   | Положительное (CW)     | `ok:t=+`   |
| `t=-`   | Отрицательное (CCW)    | `ok:t=-`   |

- В режиме STEP_DIR мотор шагает на фиксированное число шагов каждый тик
  (1 мс) в заданном направлении; в режиме UART используется `VACTUAL`
  драйвера TMC2209.
- Останавливается любой другой командой движения: `stop`, `dis`, `t=X`
  (конкретный угол), `en`, `scan=...`.
- Если драйвер был выключен, `t=+`/`t=-` включает его автоматически (без
  отдельной команды `en`).

### Сканирование сектора

Автоматическое перемещение по угловому сектору с фиксированным шагом и
задержкой на каждой позиции — режим синхронизации с внешним оборудованием
(гидроакустический тракт, камера) через пин **SYNC_OUT**.

**Зигзаг** (конечный сектор, туда-обратно до `stop`):

```
scan=start,end,step,delay
```

| Параметр | Единица | Требование                                    |
| -------- | ------- | ---------------------------------------------- |
| `start`  | °       | Начало сектора (приводится к `[0, 360)`)        |
| `end`    | °       | Конец сектора; отсчитывается от `start` **в сторону увеличения угла по кольцу** |
| `step`   | °       | Шаг, обязательно `> 0`                          |
| `delay`  | мс      | Пауза на каждой точке после прихода в неё, обязательно `> 0` |

Ответ: `ok:scan=0.00,180.00,10.00,100` — эхо приведённых к `[0, 360)`
значений. Траектория: `start → start+step → … → end → end−step → … →
start → …` — первый проход в сторону увеличения угла, далее туда-обратно
бесконечно, пока не придёт `stop`.

**Сектор через ноль.** Так как `end` отсчитывается по кольцу, `end < start`
задаёт сектор, пересекающий ноль, а не ошибку:

```
scan=350,10,5,100    # сектор 20°: 350 → 355 → 0 → 5 → 10 → 5 → 0 → 355 → 350 → …
```

Вырожденный сектор, где `start` и `end` — одна и та же точка кольца
(`scan=90,90,…`, а также `scan=0,360,…`), отвергается: полный круг
задаётся бесконечным сканом `scan=start,+,step,delay`.

**Бесконечное сканирование** (без верхней/нижней границы, до `stop`):

```
scan=start,+,step,delay     # бесконечно в сторону увеличения угла
scan=start,-,step,delay     # бесконечно в сторону уменьшения
```

Параметры `step`/`delay` — те же требования (`> 0`). Ответ:
`ok:scan=0.00,+,1.50,200`.

**Ошибки:** при нарушении любого из условий выше (вырожденный сектор
`start == end` по кольцу для зигзага, `step <= 0`, `delay == 0`) —
`err:scan\r\n`, состояние движения не меняется.

**Точность задержки:** привязана к тику опроса 1 кГц, точность ±1 мс.

Примеры:

```
scan=0,90,5,10       # зигзаг 0°–90°, шаг 5°, пауза 10 мс
scan=-45,45,2,50     # зигзаг ±45° (= сектор 315°–45° через ноль), шаг 2°
scan=350,10,5,100    # зигзаг 350°–10° через ноль, шаг 5°, пауза 100 мс
scan=0,+,1.5,200     # бесконечно вперёд от 0°, шаг 1.5°, пауза 200 мс
scan=90,-,0.5,100    # бесконечно назад от 90°, шаг 0.5°, пауза 100 мс
stop                 # остановить (любой тип движения)
```

### Синхронизация скана (sync)

Источник перехода к следующей точке скана — таймер `delay` и/или внешний
триггер по фронту **SYNC_IN** (см. [раздел SYNC](#синхронизация-с-внешним-оборудованием-sync)):

| Команда  | Действие                                                     | Ответ       |
| -------- | -------------------------------------------------------------- | ----------- |
| `sync=0` | Переход по таймеру `delay` (по умолчанию после сброса)          | `ok:sync=0` |
| `sync=1` | Переход по фронту LOW→HIGH на SYNC_IN; `delay` игнорируется     | `ok:sync=1` |
| `sync=2` | По фронту SYNC_IN **или** по `delay` как тайм-ауту — что раньше | `ok:sync=2` |
| `sync`   | Запрос состояния (см. [«Запрос состояния»](#запрос-состояния-om-hold)) | `sync=<режим> in=<0/1> out=<0/1> n=<счётчик фронтов>` |

- Учитываются только фронты, пришедшие **после** выхода SYNC_OUT в HIGH
  (точка достигнута); импульсы во время движения и до старта скана
  отбрасываются, `stop` сбрасывает ожидающий триггер.
- Требования к импульсу: длительность ≥ 1 мс (опрос 1 кГц), перед следующим
  фронтом линия должна вернуться в LOW (≥ 1 мс). Вход с pull-down.
- Значение вне `0..2` или нечисловое — строка игнорируется (как `debug=`).
- Режим действует на текущий и последующие сканы, хранится в ОЗУ
  (после сброса — `sync=0`); менять можно на лету.
- Счётчик `n` в ответе `sync` считает все фронты с момента старта в любом
  режиме — удобно для прозвонки жгута.

Типовой цикл хендшейка с сонаром: `sync=1` → `scan=...` → плата встала на
точку (SYNC_OUT=HIGH) → сонар делает замер и даёт импульс на SYNC_IN →
плата едет к следующей точке (SYNC_OUT=LOW) → …

### Удержание вала (hold)

Драйвер, удерживающий вал в точке, шумит (электрически и акустически) — это
мешает замеру. Пара команд `hold=` снимает ток с обмоток на время замера и
возвращает его обратно, **не разрушая состояние контура**:

| Команда  | Действие                                                                | Ответ       |
| -------- | ------------------------------------------------------------------------- | ----------- |
| `hold=0` | Снять удержание: движение прекращается, обмотки обесточиваются, вал свободен | `ok:hold=0` |
| `hold=1` | Вернуть удержание: ток подан, контур доводит вал к **той же** цели         | `ok:hold=1` |
| `hold`   | Запрос текущего состояния удержания (см. [«Запрос состояния»](#запрос-состояния-om-hold)) | `hold=0` / `hold=1` |

**Чем отличается от `dis`/`en`.** `dis` тоже обесточивает обмотки, но `en`
после него привязывает цель к текущей позиции и начинает всё заново. `hold=`
сохраняет всё, что нужно для продолжения работы:

- **цель** (`t=`) не меняется — после `hold=1` вал возвращается в неё;
- **точка скана** и направление зигзага не меняются — следующая точка
  считается от прежней уставки, ни одна точка не пропускается и не
  повторяется;
- **событийный кадр** (`om=1/2`) по текущей точке уже выдан и повторно не
  выдаётся — хост не получит второго `ev:1` по той же точке.

**Скан на время `hold=0` заморожен:** таймер `delay` не тикает, точка не
меняется (иначе плата «уехала» бы к следующей точке с обесточенными
обмотками, то есть пропустила бы её). Фронт SYNC_IN, пришедший за это время,
запоминается и срабатывает сразу после `hold=1`. После `hold=1` отсчёт
`delay` продолжается с того места, где был прерван.

**SYNC_OUT** за время паузы не меняется: если вал стоял на точке
(SYNC_OUT = HIGH), он остаётся HIGH.

**Сползание вала.** Без тока вал может сместиться (нагрузка, поток, вибрация).
Это не теряется: позиция в телеметрии `cp` идёт с абсолютного энкодера и
видна хосту в реальном времени, а после `hold=1` смещение отрабатывается как
обычная ошибка позиции — контур возвращает вал в цель (с той же доводкой,
что и при штатном приходе в точку). Защита от блокировки вала на время
`hold=0` не действует (обесточенный вал не обязан следовать за командой).

**Прочие взаимодействия:**

- `en` возвращает в работу целиком — в том числе снимает `hold=0` (и, как
  обычно, привязывает цель к текущей позиции). Так же поступает джог
  `t=+`/`t=-`.
- `hold=1` при выключенном приводе (`dis`) только запоминает флаг: ток
  появится по команде `en`.
- Команды `t=`, `scan=`, `sync=` в состоянии `hold=0` принимаются и
  запоминаются, но вал не тронется до `hold=1`.
- Значение вне `0..1` или нечисловое — строка игнорируется (как `debug=`).
  Состояние хранится в ОЗУ, после сброса — `hold=1`.

Типовой цикл замера (ручной, без SYNC_IN):

```
om=1                 # кадр телеметрии по приходу в точку
scan=0,180,1,5000    # шаг 1°, пауза заведомо длиннее замера
                     # ← пришёл кадр с ev:1 — вал на точке
hold=0               # тишина: обмотки обесточены
                     # ← замер сонара
hold=1               # ток вернулся, вал сел в ту же точку
                     # ← через остаток delay плата едет к следующей точке
```

С внешним триггером (`sync=1`) то же самое, но переход к следующей точке
даёт импульс на SYNC_IN уже после `hold=1`.

### Запрос состояния (om, hold)

Настройки, которых нет в телеметрии, можно не помнить на хосте, а спросить у
платы. Ключевое слово команды без аргумента — это **запрос**, а не установка:

| Команда  | Что спрашивает                                  | Ответ                    |
| -------- | ------------------------------------------------- | ------------------------ |
| `om`     | Текущий [режим выдачи телеметрии](#режим-выдачи-om) | `om=0` / `om=1` / `om=2` |
| `hold`   | Текущее [удержание вала](#удержание-вала-hold)     | `hold=0` / `hold=1`      |
| `sync`   | Режим синхронизации скана, уровни пинов и счётчик фронтов (см. [«Синхронизация скана»](#синхронизация-скана-sync)) | `sync=1 in=0 out=1 n=42` |
| `mcfg`   | Конфигурацию драйвера TMC2209 (см. [«Драйвер TMC2209»](#драйвер-tmc2209)) | `mode=STEP_DIR run=600 ...` |

**Ответ идёт без префикса `ok:`** — это состояние, а не подтверждение команды.
Одна строка, синхронно, как у любой другой команды; отличать ответ на запрос от
телеметрии просто: телеметрия разделена запятыми и начинается с `cp:`, а ответ
на запрос — одно поле `ключ=значение` (у `sync` и `mcfg` — несколько полей через
пробел).

**Установка не изменилась.** `om=1` по-прежнему отвечает `ok:om=1`, `hold=0` —
`ok:hold=0`. Различает их наличие `=`: строка `om` целиком — запрос, строка,
начинающаяся с `om=`, — установка.

**Строго без пробела.** Разбираются ровно строки `om` и `hold`: `om ` (с
хвостовым пробелом) или `OM` — это `err:unknown`, как и `sync ` (разделители
строк не подрезаются, регистр значим).

**Запрос ничего не меняет.** В частности, `om` не сбрасывает уже взведённый
событийный кадр и не влияет на скан, а `hold` не трогает обмотки.

**Когда применять.** Сразу после подключения (или переподключения) к плате:
плата могла перезагрузиться, работать с другим хостом или просто пережить
перезапуск клиента, и её фактическое состояние не обязано совпадать с тем
значением, которое хост отправлял последним. Для `hold` это ещё и вопрос безопасности — по одному
только виду не отличить обесточенный вал от стоящего под током. Референсный
клиент [SonarDebugGUI](../Software/SonarDebugGUI/) шлёт при подключении четыре
запроса подряд: `mcfg`, `sync`, `om`, `hold`.

```
> om
< om=1
> hold
< hold=0
```

**Обе прошивки** — основная и [имитатор](../Software/FW_SonarMotorDriver_Sim/) —
отвечают на запросы одинаково: парсер общий
(`Software/lib/sonar_proto/src/cmd_parser.c`), строки ответов в обеих совпадают
байт в байт.

### PID-регулятор

| Команда    | Действие              | Ответ           |
| ---------- | ----------------------- | --------------- |
| `kp=0.025` | Коэффициент Kp           | `ok:kp=0.0250`  |
| `ki=0`     | Коэффициент Ki           | `ok:ki=0.0000`  |
| `kd=0`     | Коэффициент Kd           | `ok:kd=0.0000`  |

Диапазон не ограничивается прошивкой (принимается любое конечное число) —
ответственность за разумность коэффициентов на хосте. Рекомендуемые
стартовые значения: `Kp=0.025, Ki=0, Kd=0`.

### Профиль движения (скорость и ускорение)

| Команда   | Действие                                             | Диапазон       | Ответ (успех) | Ответ (вне диапазона) |
| --------- | ------------------------------------------------------- | -------------- | -------------- | ----------------------- |
| `v=600`   | Предел скорости, °/с                                     | `1 … 1200`     | `ok:v=600.0`   | `err:bad arg (v=1..1200)` |
| `a=2000`  | Предел ускорения, °/с² (`0` = без рампы, мгновенный разгон) | `0 … 100000`   | `ok:a=2000.0`  | `err:bad arg (a=0..100000)` |

Границы диапазонов в тексте ошибки платы подставляются из текущей сборки
(`SPEED_MIN_DEG_S`, `MAX_SPEED_DEG_S`, `ACCEL_MAX_DEG_S2`) — приведённые
здесь значения соответствуют настройкам по умолчанию.

### Телеметрия (настройка)

| Команда    | Действие                                       | Ответ         |
| ---------- | ------------------------------------------------- | ------------- |
| `op=50`    | Период вывода телеметрии, мс. `0` — выключить периодическую выдачу | `ok:op=50`    |
| `om=0`     | Выдача **по таймеру** `op` (по умолчанию после сброса) | `ok:om=0`  |
| `om=1`     | Выдача **по достижению целевой позиции** (`op` не используется) | `ok:om=1` |
| `om=2`     | Оба источника: периодика по `op` **и** кадр по достижению | `ok:om=2` |
| `om`       | Запрос текущего режима выдачи (см. [«Запрос состояния»](#запрос-состояния-om-hold)) | `om=0` / `om=1` / `om=2` |
| `debug=0`  | Минимальная телеметрия (`cp`, `ec`)                | `ok:debug=0`  |
| `debug=1`  | Полная телеметрия (все поля)                       | `ok:debug=1`  |

`op` принимает `0..65535`; значения вне диапазона (парсер отклоняет
отрицательные и превышающие `65535`) не дают ответа вообще (это тот самый
«синтаксически некорректный аргумент», см. таблицу двух классов ошибок
выше). Значение `om` вне `0..2` или нечисловое — так же молча игнорируется
(как `sync=`/`debug=`). Подробности формата и полей — в разделе
[«Телеметрия»](#телеметрия), режимы выдачи — в
[«Режим выдачи (`om`)»](#режим-выдачи-om).

`op` и `om` независимы: `om` выбирает **источник** выдачи, `op` задаёт
период только для периодического источника. Чтобы замолчать полностью,
нужны обе команды — `om=0` и `op=0`; одного `op=0` при `om=1/2` мало
(событийные кадры продолжат идти), а одного `om=1` мало для тишины (кадры
пойдут по приходу в точки). `debug` действует на состав кадра в любом
режиме.

### Драйвер TMC2209

Команды применяют параметры непосредственно в чипе TMC2209 по его
собственному служебному UART (PDN_UART, отдельная линия от командного
UART платы).

| Команда         | Действие                                     | Диапазон  | Ответ (успех)      |
| --------------- | ----------------------------------------------- | --------- | -------------------- |
| `irun 600`      | Рабочий ток (при движении), мА                    | `0…3000`  | `ok:irun=600`         |
| `ihold 300`     | Ток удержания (мотор неподвижен), мА              | `0…3000`  | `ok:ihold=300`        |
| `icur 600 300`  | Оба тока одной командой: `<run_mA> <hold_mA>`     | `0…3000` каждый | `ok:icur=600,300` |
| `mstep 256`     | Микрошаг                                          | `1/2/4/8/16/32/64/128/256` | `ok:mstep=256` |
| `mcfg`          | Прочитать текущую конфигурацию драйвера (без изменений) | — | см. ниже |

**Аргумент `mstep` проверяется дважды**, и от того, на каком шаге он не прошёл,
зависит, будет ли ответ вообще:

| Что подано        | Где отсеивается                     | Реакция платы                         |
| ----------------- | ----------------------------------- | ------------------------------------- |
| `mstep 256`       | —                                    | `ok:mstep=256`                         |
| `mstep 3`, `mstep 0` | прошивка (набор микрошагов чипа)  | `err:bad arg (1/2/4/8/16/32/64/128/256)` — если драйвер готов и мотор стоит, иначе `err:not ready` / `err:busy stop motor first` (см. таблицу ниже) |
| `mstep 70000`, `mstep -1`, `mstep xyz` | парсер (`0…65535`) | **ответа нет вообще** — строка молча отбрасывается |

Парсер принимает целое `0…65535` (предел `uint16_t`, в котором хранится
микрошаг), и **значение вне этого диапазона отвергается, а не приводится к
`uint16_t`**: `mstep 65537` — это молчание, а не `ok:mstep=1`. Допустимость
самого числа — свойство чипа, а не протокола, поэтому набор `1/2/4/…/256`
проверяет уже прошивка и на неподходящее значение отвечает `err:bad arg`.
Ту же верхнюю границу до приведения типа проверяют `op=` и задержка `scan=`.

Единые коды ошибок для этой группы команд (заменяют `ok:...`):

| Ответ                              | Причина                                                        |
| ------------------------------------ | ----------------------------------------------------------------- |
| `err:not ready`                      | Драйвер TMC2209 ещё не инициализирован                            |
| `err:bad arg` / `err:bad arg (1/2/4/8/16/32/64/128/256)` | Значение вне диапазона или недопустимый микрошаг |
| `err:apply failed`                   | Ошибка обмена по UART с чипом или чип отклонил настройку           |
| `err:busy stop motor first` (только `mstep`) | Микрошаг нельзя менять во время движения — сначала `stop` |

`mcfg` состояние не меняет, только читает его — как и остальные запросы
(`sync`, `om`, `hold`, см. [«Запрос состояния»](#запрос-состояния-om-hold)):

```
> mcfg
mode=STEP_DIR run=600 hold=300 microsteps=256 ready=1
```

Поля: `mode` (`STEP_DIR` или `UART` — способ генерации шагов, задаётся
compile-time), `run`/`hold` — текущие токи в мА, `microsteps` — текущий
микрошаг, `ready` — 1, если драйвер успешно инициализирован.

### Диагностика энкодера

| Команда | Действие                                                          | Немедленный ответ | Отложенный результат |
| ------- | -------------------------------------------------------------------- | -------------------- | ----------------------- |
| `diag`  | Запустить новую серию из 16 чтений энкодера на остановленном валу     | `ok:diag`             | `enc:ok ...` / `err:enc ...` через ~16 мс (см. формат в разделе про загрузку) |

- Требует, чтобы мотор был неподвижен: если активно вращение (`t=+/-`),
  сканирование или STEP/DIR ещё в движении — команда отклоняется:
  `err:busy stop motor first`, серия не запускается.
  `stop` перед `diag` — обязателен, если до этого была команда движения.
- Результат приходит **асинхронно**, отдельной строкой, не сразу после
  `ok:diag` — образцы собираются на фоне штатного опроса энкодера
  (1 кГц), полный цикл занимает ≈ 16 мс. Формат результата такой же, как
  у стартовой диагностики: `enc:ok n=<ok>/<total> spread=<°> pos=<°>` или
  `err:enc n=<ok>/<total> spread=<°> last=<код BiSS-статуса>`.

## Телеметрия

Ничем не запрашиваемый вывод состояния. Источник выдачи задаётся командой
`om=` (по таймеру / по достижению цели / оба), период периодической
выдачи — `op=`, состав кадра — `debug=`.

- **Период по умолчанию:** 4 мс (250 Гц).
- **`debug=0` (по умолчанию)** — минимальный набор: только позиция и код
  ошибки энкодера.
  ```
  cp:179.82,ec:0
  ```
- **`debug=1`** — полный набор. Фактический период при этом не может быть
  меньше 20 мс (50 Гц) даже если `op=` задан меньшим значением — иначе
  длинная строка не успевает уйти по UART до следующего тика.
  ```
  cp:179.82,tp:180.00,pe:0.18,u:0.0563,m:cl,ec:0,kp:0.0250,ki:0.0000,kd:0.0000,v:600.0,a:2000.0,of:0,drp:0
  ```

**Поля:**

| Поле  | Тип       | Режим (`debug`) | Описание                                                        |
| ----- | --------- | ---------------- | ------------------------------------------------------------------ |
| `cp`  | float, °  | 0, 1              | Current Position — текущая позиция в `[0, 360)` (энкодер в closed-loop, виртуальный счётчик шагов в open-loop) |
| `ec`  | uint8     | 0, 1              | Error Code — код ошибки (энкодер 1–6 или блокировка вала 7), см. [таблицу ниже](#коды-ошибок-ec) |
| `tp`  | float, °  | 1                 | Target Position — текущая целевая позиция в `[0, 360)`             |
| `pe`  | float, °  | 1                 | Position Error — ошибка по кратчайшему пути, `(-180, 180]` (не арифметическое `tp − cp`) |
| `u`   | float     | 1                 | Control Output — выход PID за один тик, град/тик                   |
| `m`   | `cl`/`ol` | 1                 | Mode — closed-loop (по энкодеру) или open-loop (энкодер недоступен) |
| `kp`, `ki`, `kd` | float | 1          | Текущие коэффициенты PID (эхо последних `kp=`/`ki=`/`kd=`, либо значения по умолчанию) |
| `v`   | float, °/с | 1                | Текущий предел скорости (эхо `v=`)                                  |
| `a`   | float, °/с² | 1               | Текущий предел ускорения (эхо `a=`, `0` = выкл)                     |
| `of`  | uint32    | 1                 | Outlier Filter — счётчик показаний энкодера, отброшенных фильтром выбросов с начала работы |
| `drp` | uint32    | 1                 | Dropped — счётчик потерянных строк телеметрии с начала работы: переполнение очереди UART, а также событийный кадр, вытесненный следующим событием (см. ниже) |
| `ev`  | `1`       | 0, 1              | Event — **присутствует только в кадре, выданном по достижению цели** (`om=1/2`); всегда последнее поле строки. В периодическом кадре поля нет вовсе (не `ev:0`) |

Поля разделены запятой без пробелов, порядок фиксирован (см. примеры
выше) — парсить проще всего по `key:value` с разделителем `,`, не полагаясь
на позицию поля в строке (мало ли добавятся новые в будущих версиях).

### Режим выдачи (`om`)

| `om` | Источник кадра                                        | Роль `op`                    |
| ---- | -------------------------------------------------------- | ----------------------------- |
| `0`  | Только таймер (по умолчанию)                              | Период выдачи, `0` = молчать   |
| `1`  | Только момент прихода в целевую позицию                    | Не используется вовсе          |
| `2`  | Таймер **и** приход в позицию (кадр прихода помечен `ev:1`) | Период периодических кадров    |

Текущий режим плата отдаёт по запросу `om` (строка `om=<N>` без префикса
`ok:`) — см. [«Запрос состояния»](#запрос-состояния-om-hold).

**Что считается «достижением позиции».** Тот же критерий, что и у
[SYNC_OUT = HIGH](#синхронизация-с-внешним-оборудованием-sync): ошибка до
цели вошла в мёртвую зону (`0.05°`). Разница только в моменте: SYNC_OUT
поднимается сразу, а кадр формируется, когда отработаны доводочные шаги
(на тик-два позже — зато позиция в кадре уже окончательная).

Кадр выдаётся **по переходу** «еду → стою в цели», а не непрерывно на
стоянке: на одну заданную цель приходит ровно один кадр. Если вал вытолкнуло
из мёртвой зоны и контур вернул его обратно, придёт ещё один кадр — это тот
же самый переход, просто повторный.

**Что задаёт новую цель** (то есть даёт право на следующий событийный кадр):
`t=X`, `scan=...`, каждая очередная точка скана, а также `en` и `stop`
(обе привязывают цель к текущей позиции — кадр придёт сразу, как только вал
успокоится). Повторная `t=X` с тем же углом тоже даёт новый кадр, даже если
вал уже стоит в этой точке, — хост, пославший команду, всегда дождётся
подтверждения приходом.

**Когда кадров нет:**

- при `dis` (драйвер выключен) и в режиме непрерывного вращения `t=+`/`t=-` —
  понятия «цель достигнута» там нет;
- пока вал не дошёл до цели (в т.ч. если он вообще не может дойти — тогда
  вместо кадра придёт [`err:stall`](#защита-от-блокировки-вала-errstall)).

**Содержимое событийного кадра.** Поля `cp` и `tp` (и, соответственно, `pe`)
— снимок **момента достижения**, а не момента отправки строки: если очередь
UART была занята и кадр ушёл на 1–2 мс позже (например, скан уже поехал к
следующей точке), угол в кадре всё равно соответствует точке, к которой
привязан замер. Остальные поля (`ec`, `u`, `of`, `drp`, коэффициенты) —
текущие на момент отправки.

**Гарантия доставки.** Событийный кадр защёлкивается и ждёт освобождения
очереди TX — в отличие от периодического, который в занятом такте просто
пропускается. Защёлка одна: если очередь была занята всю дорогу до следующей
точки, новое событие вытесняет прежнее (хост получит кадр свежей точки, а не
устаревшей). Обе возможные потери — переполнение TX-буфера и такое вытеснение
— считаются в `drp`, так что пропуск точек всегда виден хосту. На практике в
`om=1` канал между точками пуст и потерь нет; риск есть только в `om=2` с
малым `op` и `debug=1`.

Примеры (`debug=0`):

```
cp:90.02,ec:0,ev:1          # om=1: пришли в точку 90°
cp:90.02,ec:0               # om=2: обычный периодический кадр
cp:100.01,ec:0,ev:1         # om=2: пришли в следующую точку скана
```

Типовое применение — сонар/камера с привязкой замера к углу: `om=1` даёт
ровно одну строку на точку скана, канал не забит потоком 250 Гц, а хосту не
нужно самому детектировать «приехали» по потоку `cp`. Аппаратный аналог того
же события — фронт SYNC_OUT в HIGH; `om=1` — его программная версия для
хостов, у которых нет проводной синхронизации.

## Асинхронные (несолиситированные) сообщения

Не всякая строка от платы — ответ на команду. Хост должен уметь принимать
следующие строки в любой момент, вне зависимости от того, отправлялась ли
соответствующая команда:

| Строка                                    | Когда приходит                                                        |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| `boot:rst=<флаги> fw=<версия>`               | Один раз сразу после старта/перезагрузки (см. [«Загрузочная последовательность»](#загрузочная-последовательность)) |
| `enc:ok ...` / `err:enc ...`                 | По завершении стартовой диагностики энкодера **или** диагностики по команде `diag` — отложенно, не в момент отправки `diag` |
| `err:motor_init=<код>`                        | Только при ошибке инициализации TMC2209 во время загрузки                   |
| `err:stall cmd=<°> meas=<°> pos=<°>`          | В любой момент во время движения в closed-loop — см. ниже                   |

### Защита от блокировки вала (`err:stall`)

Работает только в closed-loop (нужен энкодер). Если мотору скомандовано
движение, а вал по показаниям энкодера не следует за командой, плата сама
**выключает драйвер** (эквивалент `dis`, включая обесточивание обмоток) и
присылает:

```
err:stall cmd=15.3 meas=1.20 pos=87.44
```

- `cmd` — скомандованный путь за окно наблюдения, градусы;
- `meas` — фактически пройденный валом путь за то же окно, градусы;
- `pos` — позиция, на которой зафиксирована блокировка.

Срабатывает по одному из двух независимых критериев: быстрый (вал
практически неподвижен при заметной команде — реакция около 200 мс) и
медленный (вал ползёт, но проходит менее четверти скомандованного пути за
полное окно 1000 мс). Возврат в работу — обычная команда `en`. В
open-loop (энкодер недоступен) защита не действует — детектировать
блокировку без обратной связи нечем.

Помимо разовой строки `err:stall`, блокировка отражается в поле телеметрии
`ec` кодом **7** (см. таблицу ниже): в отличие от `err:stall`, который
приходит один раз, `ec:7` держится в каждом кадре телеметрии до команды
`en` — так причина остановки видна и тому, кто подключился уже после
события.

## Коды ошибок (ec)

Поле `ec` в телеметрии — не только состояние энкодера (1–6), но и код `7`
для сработавшей защиты от блокировки вала.

| `ec` | Код          | Значение                                                                                              |
| ---- | ------------ | -------------------------------------------------------------------------------------------------------- |
| 0    | OK           | Ошибок нет: энкодер отвечает корректно, защита stall не срабатывала                                      |
| 1    | BiSS CRC     | Контрольная сумма CRC6 кадра BiSS не сошлась — данные повреждены при передаче (помехи, длинный кабель без терминации, плохой контакт) |
| 2    | BiSS NO_RESP | Энкодер не ответил на опрос — проверить питание энкодера (5–12 В), трансивер THVD1452, распайку PA5/PA6/PB0/PB1, кабель |
| 3    | BiSS SENSOR  | Бит Error в кадре BiSS сброшен — энкодер сам сообщает о невалидности данных (инициализация, сбой питания) |
| 4    | BiSS WARN    | Бит Warning в кадре BiSS сброшен — предупреждение о качестве данных; в текущей логике такое чтение всё ещё считается пригодным |
| 5    | BiSS SPI     | Ошибка обмена по SPI — периферия не инициализирована, MISO не подключён, конфликт пинов                   |
| 6    | ENC OUTLIER  | Чтение отброшено фильтром выбросов (физически невозможный скачок позиции); растущий `of` при частых `ec:6` — признак помех на линии энкодера |
| 7    | STALL        | Сработала защита от блокировки вала (см. [`err:stall`](#защита-от-блокировки-вала-errstall)); драйвер выключен. Держится до команды `en`. Активная ошибка энкодера (1–6) имеет приоритет над этим кодом |

`ec` из диапазона 1–6 (ошибка энкодера) дольше 500 мс подряд переводит плату
в open-loop (`m:ol`) — см. [«Модель взаимодействия»](#модель-взаимодействия).
Код `7` (stall) на выбор режима cl/ol не влияет — это состояние привода, а не
энкодера.

## Приоритет вывода и тайминги

- У ответов на команды приоритет над телеметрией: пока в очереди передачи
  ещё есть неотправленные байты (в том числе телеметрия предыдущего тика),
  очередной тик телеметрии пропускается — это не даёт ответу команды
  «влезть» посреди уже отправляемой строки. Событийный кадр (`ev:1`) в этом
  случае не пропускается, а защёлкивается и ждёт освобождения очереди — но
  защёлка одна: если очередь была занята до самого следующего события, новое
  событие вытесняет прежнее, и потеря считается в `drp`
  (`if (g_telem_evt) g_dropped_tx++;` в `Target_MarkReached()`, `main.c`);
  подробнее — абзац «Гарантия доставки» в
  [«Режим выдачи (`om`)»](#режим-выдачи-om). Углы `cp`/`tp` в событийном
  кадре — снимок момента достижения, а не момента отправки.
- TX буферизуется в кольце по 512 байт на каждый физический порт;
  переполнение по одному из портов блокирует отправку **во все** порты
  разом (см. раздел про USART3), считается в `drp`.
- Рекомендуемый таймаут ожидания ответа на команду со стороны хоста —
  **300–500 мс** (референсный GUI-клиент использует 400 мс). Обычный ответ
  приходит за единицы миллисекунд; больший таймаут закладывает запас на
  случай, если перед ответом ещё не ушла в разделяемую очередь строка
  телеметрии.
- Диагностика энкодера (`diag`, а также стартовая) занимает ≈16 мс между
  `ok:diag` и результатом `enc:ok`/`err:enc` — на этот интервал не рассчитывайте на немедленный ответ.

## Синхронизация с внешним оборудованием (SYNC)

Отдельная от UART, чисто аппаратная часть протокола взаимодействия — два
GPIO-пина для привязки внешнего оборудования (сонар, камера) к моментам
достижения позиции при сканировании:

| Пин                | Направление | Значение                                                          |
| -------------------- | ------------ | --------------------------------------------------------------------- |
| **SYNC_OUT** (PB9)   | Выход платы   | **LOW** — началось перемещение к следующей точке сектора; **HIGH** — целевая позиция достигнута (ошибка PID в пределах deadband 0.05°) |
| **SYNC_IN** (PB12)   | Вход платы    | Внешний триггер синхронизации: в режимах `sync=1/2` фронт LOW→HIGH переводит скан к следующей точке (вход с pull-down, импульс ≥ 1 мс) |

Типичное использование: подключить SYNC_OUT к триггерному входу
гидроакустического тракта или камеры — фронт HIGH означает «антенна на
месте, можно делать замер». Работает при любом типе движения, где
актуально понятие «достигнута цель», в первую очередь — при сканировании.

Приём внешнего триггера настраивается командами
[`sync=0/1/2` и `sync`](#синхронизация-скана-sync) — одинаково в основной
прошивке и в имитаторе.

## Основная прошивка и имитатор

По UART-протоколу [имитатор](../Software/FW_SonarMotorDriver_Sim/)
неотличим от основной прошивки в штатной работе — те же команды, те же
форматы ответов и телеметрии, то же дублирование TX на USART3 (см. выше:
транспорт у прошивок общий). Единственная строка, по которой хост может
отличить имитатор от боевой прошивки, — boot-баннер: версия в нём несёт
суффикс `-sim`. Остальные отличия — во «внутренностях», непротокольные:

| Аспект                                   | Основная прошивка                     | Имитатор                                  |
| ------------------------------------------- | -------------------------------------- | -------------------------------------------- |
| Баннер `boot:rst=… fw=…`                      | Есть, `fw=1.0.0`                          | Есть, тот же формат и тот же момент выдачи, `fw=1.0.0-sim` |
| Дублирование TX на USART3 (PB10/PB11)         | Есть, USART3 на прерываниях               | Есть, USART3 на DMA — протокольной разницы нет |
| Источник `cp`                                | Реальный энкодер BiSS C                | Численная модель движения                    |
| Движение                                     | TMC2209 STEP/DIR + PID                  | Интегрирование виртуальной позиции            |
| `kp=/ki=/kd=`, `v=/a=`                       | Влияют на реальный контур               | Сохраняются и влияют на модель так же         |
| `irun/ihold/icur/mstep`                      | Пишутся в чип по UART                    | Сохраняются, отражаются в `mcfg`, на физику не влияют |
| `op=/om=/debug=`, кадр `ev:1`                 | Работают                                  | Работают так же (событие — по модели движения) |
| `ec`                                          | Реальные коды ошибок BiSS                | Всегда `0`                                    |
| `m`                                           | `cl`/`ol` по фактическому состоянию       | Всегда `cl`                                   |
| `diag` / стартовая диагностика                | Реальная серия чтений, возможен `err:enc` | Всегда `enc:ok n=16/16 spread=0.000`          |
| `err:stall`                                   | Работает                                 | Не бывает (виртуальный вал не блокируется)     |
| SYNC_OUT, SYNC_IN (`sync=`/`sync`), IWDG, LED | Работают                                 | Работают (SYNC_OUT/SYNC_IN — по модели, тот же код) |
| `hold=0/1`                                    | Обмотки реально обесточиваются           | Модель встаёт на паузу (виртуальный вал не сползает) |
| Запросы состояния `om`, `hold`, `sync`, `mcfg` | Работают                                 | Работают, те же строки ответов (парсер и обработчики общие) |

Имитатор удобен как эталон для тестирования хостового ПО (парсеры,
GUI, ROS-узлы) без подключённого мотора, энкодера и силового питания —
достаточно той же платы STM32F103C8 с другой прошивкой.

## Практические рекомендации для хоста

1. **Не парсите позиционно.** Разбирайте телеметрию и ответы по парам
   `key:value` через запятую — не по номеру поля. Формат может расширяться
   в будущих версиях прошивки (новые поля дописываются в конец строки).
2. **Отличайте тишину от ошибки.** Если на команду нет ответа вообще —
   это, скорее всего, синтаксически некорректный числовой аргумент (см.
   таблицу «Два класса ошибок разбора»), а не сбой связи. Проверяйте
   формат числа в команде в первую очередь.
3. **Не отправляйте следующую команду, не дождавшись ответа** на
   предыдущую (или явного таймаута ~400 мс) — ответы не нумеруются и не
   ссылаются на исходную команду, поэтому при частой отправке «внавал»
   сопоставить ответ с командой можно только по порядку прибытия строк, а
   между ними может втиснуться строка телеметрии или асинхронное
   сообщение (`err:stall`, `enc:ok`).
4. **Слушайте асинхронные строки постоянно**, а не только в промежутках
   между командами — особенно `err:stall`, который может прийти в любой
   момент активного движения и требует явной команды `en` для
   восстановления.
5. **При `debug=1` не завышайте `op=`** ниже 20 мс — плата сама поднимет
   период до 20 мс, но лучше не полагаться на этот клэмп и сразу задавать
   реалистичный период.
6. **Перед сменой `mstep` — `stop`.** Команда занята мотором отклоняется
   (`err:busy stop motor first`), а не выполняется отложенно.
7. **Не ждите событийный кадр там, где цели нет.** В режимах `om=1/2` кадр
   `ev:1` приходит только по приходу в заданную позицию: при `dis` и в
   непрерывном вращении (`t=+`/`t=-`) его не будет никогда, а при
   заклинившем вале вместо него придёт `err:stall`. Держите на хосте
   таймаут ожидания прихода (по времени хода сектора), а не бесконечное
   ожидание строки.
8. **`om=1` не выключает телеметрию совсем.** Чтобы плата замолчала,
   нужны обе команды: `om=0` и `op=0`.
9. **После подключения спрашивайте состояние, а не подставляйте своё.**
   Настройки, которых нет в телеметрии, плата отдаёт по запросу: `mcfg`,
   `sync`, `om`, `hold` (см. [«Запрос состояния»](#запрос-состояния-om-hold)).
   Плата могла перезагрузиться или работать с другим хостом; для `hold` это
   вопрос безопасности — обесточенный вал с виду не отличается от стоящего
   под током.
10. Автоматизированную проверку всех команд удобно свести к скрипту
   [`tools/test_commands.py`](../Software/FW_SonarMotorDriver/tools/test_commands.py)
   основной прошивки — он же служит живым примером клиента на Python.

Тот же скан, но с выдачей телеметрии по достижению точек (`om=1`) — канал
молчит между точками, на каждую точку ровно одна строка:

```
> debug=0

> om=1

> scan=0,30,10,100
```
