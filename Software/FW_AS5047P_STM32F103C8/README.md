# FW_AS5047P_STM32F103C8

Тестовая прошивка: опрос магнитного энкодера **AS5047P** по SPI, **фильтрация
угла следящим наблюдателем 2-го порядка** и вывод угла и скорости в лог.

- МК: **WeAct Studio STM32F1 Core Board** (STM32F103C8T6, HSE 8 МГц → SYSCLK 72 МГц)
- Датчик: плата **AS5047P-TS_EK_AB**
- Framework: STM32Cube HAL (PlatformIO)

## Подключение

Перемычка **JP1** на плате датчика — в положение **3V3** (тогда уровни SPI 3.3 В,
согласование с STM32 не нужно).

| AS5047P EK (UP1) | STM32F103C8T6 | Функция |
|---|---|---|
| 3V3  | 3V3 | питание |
| GND  | G   | земля |
| CSn  | PA4 | программный NSS |
| CLK  | PA5 | SPI1_SCK |
| MISO | PA6 | SPI1_MISO |
| MOSI | PA7 | SPI1_MOSI |

Лог идёт в **USB** (разъём USB-C на плате МК) — устройство определяется как
виртуальный COM-порт (класс CDC, VID:PID `0483:5740`). Отдельный USB-UART
переходник не нужен, кабель должен быть **с линиями данных**, не только питание.

Светодиод **PB2** мигает на каждой печатной строке (на классическом Blue Pill —
PC13, см. `LED_PORT`/`LED_PIN` в [main.c](src/main.c)).

Резервный канал лога — USART1: собрать с `-D LOG_USE_UART=1` в
[platformio.ini](platformio.ini), тогда вывод уходит на **PA9** (115200 8N1).

Выводы `A`, `B`, `I/PWM`, `U`, `V`, `W` на плате датчика в этом тесте не используются.

## Сборка и прошивка

```
pio run                 # сборка
pio run -t upload       # прошивка через ST-Link (SWDIO/SWCLK)
pio device list         # найти виртуальный COM-порт платы
pio device monitor      # лог (скорость у CDC-порта роли не играет)

./tools/run_filter_model.sh   # проверка фильтра на модели, на хосте, без платы
```

Код проекта собирается со строгими предупреждениями `-Wall -Wextra`
(`build_src_flags` в [platformio.ini](platformio.ini) — именно `build_src_flags`,
чтобы флаги не попали на исходники STM32Cube HAL и USB-стека ST, где они дают
лишь шум о неиспользуемых параметрах). Сборка должна проходить без единого
предупреждения в нашем коде.

После прошивки плата переподключается к хосту сама: перед стартом USB-стека
прошивка коротко прижимает D+ к земле, иначе после сброса Windows/Linux считает
устройство прежним и порт «зависает». Шапка лога печатается после того, как хост
закончил перечисление (ожидание до 3 с). Если терминал не открыт, строки просто
теряются — опрос датчика при этом не останавливается.

## Что делает прошивка

- **прерывание TIM2 с частотой 2 кГц** читает `ANGLECOM` (14 бит, 0…16383) и
  прогоняет отсчёт через следящий фильтр (см. ниже);
- каждые **100 мс** печатает отфильтрованный угол, оценку скорости и статистику
  шума за окно — размах сырого и отфильтрованного угла, СКО невязки;
- каждые **2 с** печатает диагностику `DIAAGC`/`MAG` (AGC, флаги `MAG-HIGH` /
  `MAG-LOW` / `COF`), счётчик оборотов и **измеренную длительность такта опроса**
  (по счётчику тактов ядра DWT) — видно реальную загрузку ядра;
- при сбое обмена ведёт угол по модели, считает пропуски и печатает `ERRFL`.

Пример вывода:

```
=== AS5047P + angle tracking observer ===
SYSCLK 72000000 Hz, SPI1 2250000 Hz, sample 2000 Hz
filter: type-II PLL, f_bw=50.00 Hz (max 63.66), zeta=1.00
        Kp*Ts=0.314  Ki*Ts=49.348 1/s  Bn=196.35 Hz  expected noise /2.26
columns: flt = filtered angle, w = estimated speed, p-p = peak-to-peak over window, rms = residual
    DIAG: AGC= 62  MAG= 2871  LF  turns=0
    TICK: avg 29.15 us, max 31.80 us, period 500 us, cpu 5.83%
[     123 ms] flt=180.02 deg  w=+0.15 deg/s  p-p raw/flt=12/3  rms=3.10  n=200 miss=0 gate=0
```

Колонка `p-p raw/flt` — главный наглядный результат: размах сырого угла за окно
против размаха отфильтрованного, в отсчётах (1 отсчёт = 0.022°).

## Фильтрация показаний

### Что фильтруем

Паспортный шум AS5047P — **0.068° СКО** на выходе (при включённой компенсации
DAEC; её отключение даёт выигрыш 0.016°). Это ≈ **3.1 отсчёта** из 16384, то
есть младшие ~2 бита из 14 — чистый шум. Спектр не белый: измерения на реальной
плате moteus показали **пики около 700 Гц и 2 кГц** с быстрым спадом выше.
DAEC компенсирует динамическую ошибку (задержка тракта после коррекции 1.9 мкс
на ABI/UVW), но с шумом квантования и АЦП не борется — это задача МК.

### Что говорят публикации

Литература по обработке сигнала датчиков угла делится на три подхода.

**1. Сглаживание по углу (скользящее среднее, БИХ-ФНЧ 1-го порядка.)**
Самый частый совет в прикладных источниках и самый вредный для датчика
положения: любой ФНЧ по позиции вносит фазовую задержку, а задержка на
вращающемся валу — это **ошибка угла, линейно растущая со скоростью**. В
патентной литературе по приводам такие фильтры применяют к *скорости*
(КИХ-усреднение по N точкам плюс БИХ для подавления боковых лепестков), а не
к положению, и прямо отмечают, что низкая частота среза, нужная для подавления
шума квантования, увеличивает фазовое запаздывание.

**2. Следящий наблюдатель угла (angle tracking observer, ATO) — он же цифровая
ФАПЧ.** Контур с ПИ-регулятором, который «догоняет» измеренный угол: интегратор
даёт оценку скорости, вторая интеграция — оценку угла. Ключевое свойство:
это система **типа II**, у неё нулевая установившаяся ошибка по линейно
нарастающему входу, то есть на постоянной скорости фильтр **не отстаёт вообще**,
продолжая подавлять шум как ФНЧ 2-го порядка. Ограничение известно: на
постоянном *ускорении* тип II оставляет конечную ошибку, поэтому в работах по
безредукторным приводам предлагают ATO типа III и IV с доп. компенсацией.
Jason Sachs формулирует основной довод против конечных разностей: «если я
измеряю положение 10 000 раз в секунду, а скорость считаю вычитанием положения
секундной давности, я игнорирую информацию в остальных 9 998 отсчётах».
Практическое подтверждение — moteus: ADPLL по показаниям того же AS5047P,
коэффициенты берутся как `Kp = 2·ζ·ω`, `Ki = ω²`, полоса 100 Гц, ζ = 1;
результат — около 6 дБ снижения акустического шума привода.

**3. Фильтр Калмана.** Работы по магнитным и аналоговым энкодерам показывают
хорошую точность (в одной из них абсолютная ошибка удерживается в пределах
0.03°). Но с моделью «постоянная скорость» установившийся фильтр Калмана
**вырождается ровно в тот же контур типа II с постоянными коэффициентами** —
матрица усиления сходится к константе. Платой за формально более общий подход
становятся матричные операции на каждом шаге; в литературе по трекинговым
контурам GNSS это прямо названо критичным для реального времени, и целые статьи
посвящены снижению этой стоимости (таблицы для вычисления усиления, вынос
преобразований координат из контура). Адаптировать усиление здесь не по чему:
шум энкодера стационарен, его СКО известно из datasheet и не меняется.

### Выбор

Реализован **следящий наблюдатель 2-го порядка (тип II) с отбраковкой
выбросов** — [angle_filter.h](include/angle_filter.h),
[angle_filter.c](src/angle_filter.c).

Шаг фильтра построен как «прогноз — невязка — коррекция»:

```
theta = theta + Ts * omega            // прогноз на текущий такт
e     = wrap(raw - theta)             // невязка (фазовый детектор)
omega = omega + Ki * Ts * e           // коррекция скорости
theta = theta + Kp * Ts * e           // коррекция угла

Kp = 2 * zeta * wn,  Ki = wn^2,  wn = 2*pi*f_bw
```

Порядок важен: коррекция после прогноза, поэтому после `angle_filter_update()`
состояние относится к моменту **только что принятого измерения**, а не к
следующему такту, и «нулевое запаздывание» выполняется буквально.

Побочная выгода — оценка скорости получается бесплатно, без численного
дифференцирования, которое усиливало бы шум квантования.

### Проверка на модели

Фильтр не зависит ни от HAL, ни от `math.h`, поэтому проверяется хостовым gcc —
вместе с **тем же самым** `src/angle_filter.c`, который уходит в прошивку.
Прогон одной командой (Git Bash или любой `sh`):

```
./tools/run_filter_model.sh
```

Скрипт собирает [tools/filter_model.c](tools/filter_model.c) с настоящим
`src/angle_filter.c` и печатает все числа этого раздела. Параметры берутся из тех
же макросов, что и в `platformio.ini`, и переопределяются переменными окружения:
`FILTER_BW_HZ=20.0f ./tools/run_filter_model.sh`.

Модель датчика: истинный угол по сценарию + гауссов шум **3.1 отсчёта СКО**
(паспортные 0.068°) + округление до отсчёта (14 бит), fs = 2 кГц. Генератор
псевдослучайных чисел свой, прогон детерминирован. Окно измерения — 200 000
отсчётов (100 с) после 2 с прогрева.

Сравнение **при одинаковом уровне выходного шума** — скользящее среднее N = 5,
однополюсный БИХ α = 0.30 и данный контур с полосой 50 Гц:

| Скорость | Сырой, СКО | MA(5) СКО / запазд. | БИХ(0.3) СКО / запазд. | **Контур 50 Гц** СКО / запазд. |
|---|---|---|---|---|
| 0 об/мин    | 0.0685° | 0.0307° / +0.0001° | 0.0288° / +0.0001° | **0.0316° / +0.0001°** |
| 60 об/мин   | 0.0685° | 0.0306° / −0.3600° | 0.0288° / −0.4200° | **0.0316° / +0.0000°** |
| 600 об/мин  | 0.0685° | 0.0307° / −3.5999° | 0.0288° / −4.1999° | **0.0316° / +0.0001°** |
| 3000 об/мин | 0.0685° | 0.0306° / −17.9999° | 0.0288° / −20.9999° | **0.0316° / +0.0001°** |

СКО здесь — разброс вокруг среднего, «запаздывание» — само среднее ошибки.
Шум на выходе у всех трёх близок (0.029…0.032°), но у сглаживающих запаздывание
растёт линейно со скоростью и на 3000 об/мин достигает 18–21°, а у следящего
контура остаётся нулевым: измеренное смещение не выходит за **0.0001°**
(0.005 отсчёта) на всём диапазоне 0…12000 об/мин — это уровень статистической
погрешности самого прогона, а не систематическое запаздывание.

Остальные проверенные свойства (сценарии 2–7 в выводе скрипта):

- **подавление шума** на месте: 0.0685° → 0.0316° СКО (в 2.17 раза) при
  f_bw = 50 Гц; теоретическая оценка `sqrt(fs / 2·Bn)` даёт 2.26 — расхождение
  объясняется искажением полосы при явной дискретизации (`wn·Ts` = 0.157);
- **ошибка на ускорении** (плата за тип II): −0.0250° при 10 об/с², −0.2501° при
  100 об/с². Совпадает с теорией `−(1 − Kp·Ts)·a/wn²` (−0.0250° и −0.2502°);
- **одиночный выброс** (испорченный отсчёт со скачком на 180°) не вносит в оценку
  ничего: состояние после него **бит в бит** совпадает с тактом, целиком
  проведённым по модели. Цена выброса — только пропущенная коррекция: от чистого
  прогона оценка отходит максимум на **0.06 отсчёта** (0.0013°) и возвращается за
  6 тактов (3 мс);
- **настоящий скачок** (вал реально ушёл на 90°) распознаётся по серии
  отбраковок — 16 отсчётов, 8 мс, — после чего контур перезахватывается; слежение
  полностью восстанавливается через 18 отсчётов (9 мс): два первых отсчёта уходят
  на захват;
- **потерянные отсчёты** (5 % на 600 об/мин) ведутся по модели и смещения не
  накапливают: на 10 090 пропусков из 204 000 тактов среднее −0.003 отсчёта, СКО
  1.444 против 1.423 отсчёта на том же прогоне без пропусков, максимум за 100 с —
  6.8 отсчёта (0.15°), перезахватов нет;
- **холодный захват на вращающемся валу**: начальная скорость берётся по разности
  двух первых отсчётов, поэтому и на 3000, и на 20000 об/мин фильтр входит в режим
  без перезахватов — ошибка через 100 мс 0.23 и 0.50 отсчёта.

Чего этой моделью проверить нельзя: спектр шума настоящего датчика (в модели он
белый, а у AS5047P есть пики около 700 Гц и 2 кГц), джиттер такта опроса,
нелинейность самого AS5047P и работу DAEC. Это видно только на плате — по
колонкам `p-p raw/flt` и `rms` в логе.

### Настройка

В [platformio.ini](platformio.ini):

```
-D SAMPLE_RATE_HZ=2000U   ; частота опроса (такт TIM2), должна делить 1 МГц нацело
-D FILTER_BW_HZ=50.0f     ; полоса контура
-D FILTER_DAMPING=1.0f    ; zeta, 1.0 = критическое демпфирование
```

`FILTER_DAMPING` = 1.0 — критическое демпфирование в смысле полюсов: они
вещественные, колебаний в переходном процессе нет. Но «без перерегулирования»
это не значит: у контура типа II есть ноль от пропорциональной ветви, и на
скачке угла оценка выходит за цель. По модели — на **9.9 %** при f_bw = 50 Гц
(у непрерывного контура при ζ = 1 это ровно 1 + e⁻² = 13.5 %, и при более узкой
полосе дискретный прогон к той же цифре сходится: 13.2 % при f_bw = 5 Гц).
Уменьшается выброс только ростом ζ: 1.9 % при ζ = 2. Для датчика положения он
не мешает — скачок угла это либо помеха, которую отбрасывает порог, либо потеря
захвата, — поэтому ζ = 1 оставлено.

Компромисс полосы на fs = 2 кГц (модель, вход 3.1 отсчёта = 0.068° СКО):

| f_bw | Шум на выходе | Запаздывание при 100 об/с² |
|---|---|---|
| 10 Гц | 0.0135° | −8.546° |
| 20 Гц | 0.0194° | −1.993° |
| 50 Гц | 0.0316° | −0.250° |
| 63 Гц | 0.0360° | −0.139° |

Уже полоса — чище угол, но хуже отработка ускорения. Потолок при 2 кГц —
**63.66 Гц**: столько разрешает `angle_filter_init()`, ограничивая `wn·Ts ≤ 0.2`.
Это не предел устойчивости, а запас перед ним: по модели явная дискретизация
теряет устойчивость при `wn·Ts ≈ 0.825` (теория для ζ = 1: 2√2 − 2 ≈ 0.828), то
есть около 263 Гц при 2 кГц — рабочее ограничение вчетверо ниже. Нужна бо́льшая
полоса — поднимайте частоту опроса, а не только `FILTER_BW_HZ`.

Порог отбраковки выбросов — `ANGLE_FILTER_GATE_DEFAULT` (512 отсчётов) и
`angle_filter_set_gate()`. Важно: невязка сравнивается с **прогнозом**, поэтому
порог ограничивает не скорость вращения (на установившейся скорости невязка
равна шуму при любых оборотах), а мгновенный скачок — 512 отсчётов за такт при
2 кГц соответствует рывку сразу до ~3750 об/мин.

### Почему опрос в прерывании

Следящему фильтру нужен **строго равномерный шаг Ts**: коэффициенты `Kp·Ts` и
`Ki·Ts` посчитаны под фиксированный период, и джиттер такта напрямую
превращается в ошибку оценки скорости. Печать в USB CDC блокирующая (ждёт, пока
хост заберёт пакет) и в прежней схеме «опрос в главном цикле» дала бы разброс
периода в миллисекунды. Поэтому **весь обмен с датчиком перенесён в прерывание
TIM2**, а главный цикл только снимает копию состояния и печатает; диагностические
регистры читаются по заявке из того же прерывания, чтобы SPI имел одного хозяина.

Приоритеты прерываний: SysTick 0, TIM2 1, USB 5. SysTick обязан быть выше TIM2 —
иначе таймауты HAL внутри обработчика опроса не истекали бы (`HAL_GetTick()`
перестал бы расти).

Загрузка ядра тактом опроса печатается самой прошивкой (строка `TICK`) — по
расчёту это ~30 мкс из 500 мкс периода, то есть ~6 %.

### Своя конфигурация HAL

`include/stm32f1xx_hal_conf.h` вместе с
`board_build.stm32cube.custom_config_header = yes` в `platformio.ini` делает
сборку независимой от соседних проектов. Раньше своего заголовка у проекта не
было, и он брал общий `stm32f1xx_hal_conf.h` из каталога пакета
`framework-stm32cubef1`. Пакет один на все прошивки репозитория: сборка
проекта со своим заголовком общий файл оттуда удаляет, а сборка без него —
создаёт его заново из шаблона ST. Поэтому проект собирался или не собирался в
зависимости от того, какую прошивку собрали перед ним («Implicit dependency
stm32f1xx_hal_conf.h not found»). Содержимое повторяет шаблон ST, из которого
раньше и создавался общий файл, но включены только нужные модули HAL, поэтому
прошивка осталась байт-в-байт прежней.

## Особенности протокола AS5047P

- SPI режим 1 (CPOL=0, CPHA=1), MSB first, кадр 16 бит, до 10 МГц (здесь 2.25 МГц);
- бит 15 кадра — чётность (even) по битам 14…0, бит 14 — R/W (команда) или EF (ответ);
- данные регистра приходят **следующим** кадром, поэтому одно чтение = два обмена;
- между кадрами CSn обязан подниматься (t_CSn ≥ 350 нс) — в драйвере это `delay_cs()`.
