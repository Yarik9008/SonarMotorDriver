# SonarDebugGUI — отладчик FW_SonarMotorDriver

Графическое приложение (PySide6, тёмная тема) для проверки
основной прошивки [FW_SonarMotorDriver](../FW_SonarMotorDriver): управление мотором,
PID, токи/микрошаг, сканирование, живая телеметрия и **2D сонарная диаграмма (PPI)**
положения гидроакустической антенны.

Работает как с реальной платой (USB-UART, 115200 8N1), так и со **встроенным
симулятором прошивки** — то есть полностью без железа.

## Возможности

- **Команды протокола — каждая своим элементом интерфейса**: `en`/`dis`/`stop`,
  `t=<°>`, `t=+`/`t=-`, `v=`/`a=` (скорость/ускорение), `kp=`/`ki=`/`kd=`,
  `op=`, `om=` (источник кадра телеметрии), `debug=`, `hold=` (удержание вала),
  `scan=…` (сектор и бесконечный), `sync=…`/`sync`, `irun`/`ihold`/`icur`,
  `mstep`, `mcfg`. Единственная команда протокола без своей кнопки — `diag`:
  её отправляют из вкладки «Консоль», ответ `enc:ok …`/`err:enc …` приходит
  в журнал, как любая асинхронная строка.
- **Опрос состояния при подключении**: сразу после установления связи GUI шлёт
  плате четыре запроса — `mcfg`, `sync`, `om`, `hold`. Плата могла
  перезагрузиться или работать с другим хостом, поэтому режим выдачи
  телеметрии и удержание вала берутся из её ответа, а не из последнего выбора
  оператора (для `hold` это ещё и вопрос безопасности: под током ли вал, за
  который собрались браться руками). Ответы на запросы приходят **без
  префикса `ok:`** (`om=1`, `hold=0`) и выправляют виджеты напрямую, минуя
  охранники «последнего подтверждённого значения», — обратная команда на плату
  при этом не уходит.
- **Поля телеметрии**: `cp`, `tp`, `pe`, `u`, `ec`, `drp`, `kp`/`ki`/`kd`,
  `v`, `a` — каждое со своим индикатором, `m` (`cl`/`ol`) — цветом на
  PPI-диаграмме. Счётчик выбросов энкодера `of` и метка событийного кадра
  `ev:1` парсером разбираются, но отдельного индикатора у них нет — их видно
  сырыми в журнале RX.
- **Режим синхронизации скана** (раздел «Сканирование»): выбор источника
  перехода к следующей точке — таймер / фронт SYNC_IN / SYNC_IN с тайм-аутом
  (`sync=0/1/2`) — и индикатор: подтверждённый режим, уровни SYNC_IN/SYNC_OUT,
  счётчик фронтов (кнопка «⟳» шлёт запрос `sync`). Во встроенном симуляторе
  пина SYNC_IN нет, поэтому при `sync=1` скан честно стоит на точке.
- **Джог**: обычные кнопки — вращение на настроенной скорости (v=, по умолчанию
  максимум 1200 °/с); пресет «Медленно» (30 °/с) — для точной подводки.
  Удержание — вращение, отпускание — стоп и возврат настроенной скорости.
- **PPI-диаграмма**: луч текущего угла (`cp`), призрак цели (`tp`), сектор скана,
  послесвечение-«свип», цветовая индикация режима (cl/ol) и ошибки энкодера (`ec`).
- **Живые графики** телеметрии (cp/tp/pe/u) с паузой, очисткой и экспортом в CSV.
- **Встроенный симулятор** прошивки: те же строки ответов и телеметрии, что у железа.
- **Консоль** для сырых команд + журнал TX/RX (дублируется в `logs/`).
- **Защита от «молчания» прошивки**: аргументы вне диапазона отсекаются на клиенте,
  а на команды без ответа срабатывает таймаут-предупреждение.

Слева — сворачиваемые разделы управления (Мотор, PID, Сканирование) плюс
«Подключение» (канал связи + период/режим телеметрии). Справа — три
переключаемые вкладки: **Диаграмма** (PPI), **Графики** и **Консоль**.
Настройки драйвера TMC2209 (токи движения/удержания, микрошаг, `mcfg`) входят
в раздел «Мотор». Показания телеметрии (`tp`/`pe`/`ec`/`drp`) тоже в «Моторе»,
выход регулятора (`u`) — в «Регуляторе PID», рядом с параметрами, к которым они
относятся.

## Установка

Требуется Python 3.10+.

```
cd Software/SonarDebugGUI
pip install -r requirements.txt
```

Зависимости: `PySide6`, `pyqtgraph`, `pyserial` (первая установка объёмная).

Всё это нужно только самому GUI. Проверкам из раздела
[«Проверка без железа»](#проверка-без-железа) не нужен ни Qt, ни `pyserial`:
`protocol.py` и `simulator.py` от Qt не зависят, а режим `--sim` порт не
открывает (импорт `pyserial` в `protocol_test.py` обёрнут в `try`).

## Запуск

```
python run.py
```

### Без железа (симулятор)
1. Выберите «Симулятор» → «Подключить».
2. Пойдёт поток телеметрии, стрелка на диаграмме оживёт.
3. Пробуйте: `Перейти` на угол, толчки CW/CCW, `Старт скана`, PID, токи, `mcfg`.

### С реальной платой
1. Подключите USB-UART адаптер к плате: **PA9 (TX) → RX**, **PA10 (RX) → TX**, **GND**.
2. Выберите «Реальный COM», порт определяется автоматически (кнопка «Обновить»).
3. «Подключить» (115200 8N1).

> Совет: в ту же плату можно залить имитатор —
> [`pio run -e sim`](../FW_SonarMotorDriver/README.md#имитатор-envsim) того же
> проекта прошивки: он отвечает тем же протоколом без мотора и энкодера.

## Проверка без железа

Два прогона, оба на виртуальных часах (шаг модели 1 мс = период главного цикла
прошивки), оба детерминированы и COM-порт не открывают:

```bash
cd Software/SonarDebugGUI
python -m unittest discover -s tests   # юнит-тесты протокола и модели прошивки
python protocol_test.py --sim          # конформанс-тест протокола на модели
```

- **`tests/`** — пять модулей, всего 169 тестов:
  - `test_protocol.py` (45) — формат кадров телеметрии, парность
    `format_telemetry`/`parse_telemetry`, валидаторы диапазонов, кольцевая
    арифметика;
  - `test_simulator.py` (91) — модель прошивки: кратчайший путь, профиль
    движения, разбор аргументов, скан, `sync`/`om`/`hold`, сборка строк из
    кусков потока, запросы состояния `om`/`hold`;
  - `test_board_constants.py` (11) — страховка от расхождения чисел: читает
    `board.h` основной прошивки, а также её `lib/sonar_proto/src/cmd_parser.c`
    (пределы токов) и `lib/tmc2209/src/tmc2209.c` (набор микрошагов), и
    сверяет их с константами, объявленными в `sonar_gui/protocol.py`;
  - `test_firmware_commands.py` (7) — страховка от расхождения команд: читает
    `cmd_parser.h`/`cmd_parser.c` и требует, чтобы каждая команда парсера (в том
    числе запросы `om` и `hold`) была покрыта построителем, валидатором и
    ожиданием модели, а числовые границы аргументов, записанные в `cmd_parser.c`
    литералами (токи, `op=`, `om=`, `sync=`, пауза скана, `mstep`), совпадали
    с константами `protocol.py`;
  - `test_cmd_parser_host.py` (15) — единственный модуль, который не
    читает исходники прошивки, а **исполняет** их: собирает хостовым gcc
    настоящий `lib/sonar_proto/src/cmd_parser.c` зондом
    `lib/sonar_proto/tools/cmd_parser_probe.c` и сверяет разбор каждой
    строки корпуса с моделью `simulator.py` и с построителями
    `protocol.py`, а границы аргументов — исполнением на границе
    (предел принимается, предел ± 1 отвергается). Регулярочные проверки
    выше не различают `strcmp` и `strncmp`, этот модуль различает.
    **Если компилятора C в PATH нет, класс пропускается** (`skipTest`
    с пояснением, где искали): весь прогон печатает тогда
    `Ran 157 tests … OK (skipped=1)` вместо 169 и остаётся зелёным.

  Запускать именно из `Software/SonarDebugGUI`: `python -m` кладёт рабочий
  каталог в `sys.path`, поэтому пакет `sonar_gui` импортируется без установки,
  а ключ `-t` не задаётся сознательно — с ним `unittest` потребовал бы
  `tests/__init__.py`.
- **`protocol_test.py --sim`** — тот же список проверок, что и на живой плате
  (`python protocol_test.py COM25`), но против Python-модели прошивки
  `sonar_gui/simulator.py`. Аппаратно-зависимые ветки (`mcfg ready`, `err:enc`,
  фронты SYNC_IN) в модели недостижимы — что именно она упрощает, перечислено
  в шапке `simulator.py`.

Числа в скобках и 184 проверки конформанса — из локального прогона
(`Ran 169 tests … OK` и `ИТОГО: 184/184 пройдено`, замер 2026-09-18 на
Python 3.14.7 с gcc 13.2.0 в PATH). Сверить у себя — теми же двумя
командами выше.

Оба прогона должен выполнять CI —
[.github/workflows/ci.yml](../../.github/workflows/ci.yml), но **ни одного
прогона на раннере ещё не было**: файл workflow не закоммичен и на origin
отсутствует.

## Диаграмма антенны

Прошивка отдаёт угол вала `cp` в градусах. Реального редуктора между валом и антенной
в прошивке нет, поэтому пересчёт задаётся тремя полями («Передаточное число»,
«Смещение нуля», «Направление») в разделе **«Мотор»** — это чисто локальная
настройка GUI, в прошивку она не отправляется (по умолчанию передаточное число 1):

```
угол_антенны = sign · (cp · передаточное_число) + смещение_нуля
```

## Структура

```
SonarDebugGUI/
├── run.py                     — запуск GUI
├── protocol_test.py           — конформанс-тест протокола (плата или --sim)
├── requirements.txt           — зависимости GUI (тестам не нужны)
├── tests/                     — юнит-тесты на stdlib unittest (без Qt)
│   ├── _support.py            — общая обвязка: модель на виртуальных часах
│   ├── test_protocol.py       — форматы, валидаторы, построители команд
│   ├── test_simulator.py      — модель прошивки: углы, профиль, скан, sync/om/hold
│   ├── test_board_constants.py — сверка констант хоста с board.h прошивки
│   └── test_firmware_commands.py — сверка покрытия с парсером прошивки
└── sonar_gui/
    ├── app.py                 — QApplication + тема + окно
    ├── main_window.py         — сборка и связи всех виджетов
    ├── protocol.py            — единый источник правды: команды/телеметрия/константы
    ├── controller.py          — DeviceClient: валидация, таймаут ответа, маршрутизация
    ├── simulator.py           — Python-модель прошивки (без Qt)
    ├── logger.py              — журнал TX/RX в logs/
    ├── theme.py, dark.qss     — тёмная тема
    ├── transport/             — Transport: SerialTransport (COM) и SimTransport (симулятор)
    └── widgets/               — PPI-диаграмма, графики и панели управления
```

## Соответствие протоколу

Форматы команд и телеметрии повторяют прошивку: `FW_SonarMotorDriver/src/main.c`
и парсер `cmd_parser.c`, который теперь живёт в общей библиотеке
[`lib/sonar_proto`](../FW_SonarMotorDriver/lib/sonar_proto/README.md) (одна копия на прошивку
и имитатор). Что расхождение не накопится, следит `tests/test_firmware_commands.py`:
он разбирает исходники парсера и требует покрытия для каждой команды.
Автотест на реальной плате из
[`FW_SonarMotorDriver/tools/test_commands.py`](../FW_SonarMotorDriver/tools/test_commands.py)
использует тот же набор команд.
