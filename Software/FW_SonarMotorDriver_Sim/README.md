# FW_SonarMotorDriver_Sim — имитатор UART-протокола

Отладочная прошивка для STM32F103C8 (та же плата, что и основная). По линии связи
**неотличима от основной прошивки в штатной работе**: принимает все команды,
отвечает теми же строками и шлёт ту же телеметрию. Портов, как и у основной
прошивки, два: USART1 (PA9 TX / PA10 RX) и дублирующий USART3 (PB10 TX / PB11 RX),
оба на 115200 8N1 — TX уходит в оба сразу, RX сливается в один поток команд
(транспорт общий, см. ниже). Единственная строка, по которой хост отличит
имитатор от боевой прошивки, — boot-баннер: `fw=1.0.0-sim` вместо `fw=1.0.0`.

**Внутри нет реального функционала:**

- нет обмена с энкодером LENZ IRS (SPI/BiSS C не инициализируются);
- нет управления TMC2209 (USART2, TIM4/STEP/DIR не используются; пин ENN = HIGH,
  драйвер принудительно выключен на случай прошивки в реальную плату).

Назначение: отладка ПО верхнего уровня (парсеры телеметрии, GUI, ROS-узлы и т.п.)
без подключённого мотора, энкодера и силового питания. Функционал синхронизации
реализован полноценно и одинаково с основной прошивкой — SYNC_OUT и внешний
триггер SYNC_IN (команды `sync=`/`sync`, см. раздел
[«Синхронизация»](#синхронизация-sync_out--sync_in)).

Снятие удержания вала на время замера (`hold=0` / `hold=1`) имитатор
поддерживает протокольно: модель движения встаёт на паузу, скан замораживается,
цель и точка скана сохраняются — как в основной прошивке (описание —
[Protocol.md](../../Docs/Protocol.md#удержание-вала-hold)).

Запросы состояния — `mcfg`, `sync`, `om`, `hold` (ключевое слово без `=`) —
имитатор обслуживает теми же строками, что и основная прошивка: `om=<0..2>` и
`hold=<0|1>` **без префикса `ok:`** (это состояние, а не подтверждение команды).
Парсер и обработчики общие, расходиться нечему. Установка при этом не
изменилась: `om=1` по-прежнему отвечает `ok:om=1`. Подробности —
[Protocol.md](../../Docs/Protocol.md#запрос-состояния-om-hold).

## Модель движения

Виртуальная позиция движется к цели с ограничением скорости `MAX_SPEED_DEG_S`
(1200°/с), квантуется в микрошаги (256 × 200/об), deadband 0.05° — числа в
телеметрии выглядят как у реального привода в open-loop. При старте позиция
инициализируется значением 37.5° и «уезжает» в 0° — имитация хоминга после сброса.

Телеметрия всегда показывает штатную работу: `ec:0`, режим `m:cl`.

## Отличия от основной прошивки (протокольно незаметные)

| Аспект | Основная | Имитатор |
| ------ | -------- | -------- |
| Баннер `boot:rst=… fw=…` | есть, `fw=1.0.0` | есть, тот же код и момент выдачи, `fw=1.0.0-sim` |
| Командный UART | USART1 (DMA) + USART3 (прерывания, `UART3_USE_DMA` = 0) | USART1 (DMA) + USART3 (**DMA**, `UART3_USE_DMA` = 1) — DMA1 у имитатора свободно |
| Неудачная инициализация UART | 3 попытки, дальше работа без командного канала (быстрое мигание LED) | попытки без ограничения: `while (UART_Init() != 0) { }` |
| Позиция `cp` | энкодер BiSS C | виртуальная модель |
| Движение | TMC2209 STEP/DIR + PID | численное интегрирование |
| `kp=/ki=/kd=` | влияют на PID | сохраняются, echo в телеметрии |
| `v=/a=` (скорость/ускорение) | ограничивают контур управления | влияют на модель движения так же |
| `irun/ihold/icur/mstep` | пишутся в чип по UART | сохраняются, отражаются в `mcfg` |
| `ec` (код ошибки) | реальные ошибки BiSS | всегда 0 |
| `m` (режим) | cl/ol по состоянию энкодера | всегда cl |
| Диагностика энкодера (старт и `diag`) | реальная серия чтений BiSS, возможен `err:enc` | всегда `enc:ok n=16/16 spread=0.000` |
| Фильтр выбросов энкодера (`ec:6`, поле `of`) | отбрасывает неправдоподобные показания | нет выбросов, `of:0` |
| Защита от блокировки вала (`err:stall`) | вал стоит ≥1 с при команде движения → драйвер выключается | нет (виртуальный вал не блокируется) |
| Режим выдачи телеметрии `om=` (кадр `ev:1` по достижению цели) | работает | работает (событие — по модели движения) |
| SYNC_OUT (PB9) | работает | работает (по модели) |
| SYNC_IN (PB12), команды `sync=`/`sync` | работают | работают (тот же код, переход точки скана — по модели) |
| Удержание вала `hold=0/1` | обмотки реально обесточиваются | модель встаёт на паузу (виртуальному валу нечем сползать) |
| Запросы состояния `mcfg`, `sync`, `om`, `hold` | работают | работают, те же строки ответов (общий парсер) |
| IWDG, LED PC13 | работают | работают |

## Синхронизация (SYNC_OUT / SYNC_IN)

Имитатор реализует полноценный аппаратный хендшейк с внешним оборудованием
(сонар, камера):

- **SYNC_OUT (PB9)** — как в основной прошивке: **LOW** — началось движение к
  точке скана, **HIGH** — точка достигнута (по модели движения).
- **SYNC_IN (PB12)** — внешний триггер (вход, pull-down): опрос 1 кГц,
  детектор фронта LOW→HIGH. Импульс должен длиться ≥ 1 мс; перед следующим
  фронтом линия должна вернуться в LOW (≥ 1 мс).

Источник перехода к следующей точке скана выбирается командой `sync=N`
(действует на текущий и последующие сканы, ответ `ok:sync=N`):

| Команда  | Переход к следующей точке | Параметр `delay` из `scan=` |
| -------- | -------------------------- | ---------------------------- |
| `sync=0` | по таймеру (по умолчанию — поведение основной прошивки) | пауза на точке, мс |
| `sync=1` | по фронту SYNC_IN          | игнорируется                 |
| `sync=2` | по фронту SYNC_IN **или** по таймеру — что раньше | тайм-аут ожидания триггера, мс |

Учитываются только фронты, пришедшие **после** выхода SYNC_OUT в HIGH
(точка достигнута); импульсы во время движения и до старта скана
отбрасываются. `stop` сбрасывает ожидающий триггер.

Команда `sync` (запрос) отвечает строкой:

```
sync=<режим> in=<уровень SYNC_IN> out=<уровень SYNC_OUT> n=<счётчик фронтов SYNC_IN>
```

Счётчик `n` считает все фронты с момента старта (в любом режиме) — удобно
для прозвонки жгута. Типовой цикл с сонаром: `sync=1` → `scan=0,90,10,100` →
плата встала на точку (SYNC_OUT=HIGH) → сонар делает замер и даёт импульс на
SYNC_IN → плата едет к следующей точке (SYNC_OUT=LOW) → …

Команды `sync=`/`sync` и вся логика SYNC_IN реализованы **одинаково в
имитаторе и в основной прошивке** (перенесён тот же код, см.
[Protocol.md](../../Docs/Protocol.md#синхронизация-скана-sync)). Пока
`sync=` не подана, скан шагает по таймеру `delay`, как раньше.

## Структура проекта

```
FW_SonarMotorDriver_Sim/
├── platformio.ini
├── openocd/
│   └── wch-link.cfg       — конфиг адаптера WCH-Link (тот же, что в FW_SonarMotorDriver)
├── include/
│   ├── board.h            — свои константы пинов/скорости/PID; блок UART_*/UART3_* совпадает с прошивкой, кроме UART3_USE_DMA (у имитатора DMA свободно)
│   └── stm32f1xx_hal_conf.h
└── src/
    └── main.c             — модель движения, сканирование, синхронизация, команды, телеметрия (написан для имитатора)
```

Никакого `lib/tmc2209`, `biss_c.*`, `pid.*`, `tools/`, `test/` — в этом проекте нет ни реального драйвера, ни тестов, ни утилит.

Командный протокол имитатор не копирует, а берёт из общей библиотеки
[`../lib/sonar_proto`](../lib/sonar_proto/README.md) — той же самой, что и основная
прошивка (`uart.c`, `line_reader.c`, `cmd_parser.c`). Подключение — через
`lib_deps = symlink://../lib/sonar_proto` в `platformio.ini`; библиотека
берёт `board.h` отсюда, из `include/`, поэтому выводы, скорости и выбор DMA/IT
остаются имитаторскими. Раньше это были копии файлов, и имитатор успел отстать от
прошивки на три исправления UART: удержание участка TX-кольца до конца передачи,
снятие RXNE у ещё не готового USART3 и корректный разбор ошибок линии в
`HAL_UART_ErrorCallback`. Теперь расходиться нечему.

> **Этот драйвер на плате с имитатором не запускался ни разу.** Общий `uart.c`
> проверялся на железе только в составе основной прошивки, а условия у имитатора
> другие: USART3 он поднимает на DMA (`UART3_USE_DMA` = 1 против `0` у прошивки),
> и каналы DMA1 разложены иначе — у основной прошивки Ch2/Ch3 заняты SPI1
> энкодера, здесь SPI1 нет вовсе. Что проверено: сборка без предупреждений,
> наличие `USART3_IRQHandler`, `UART_Init` и строк `boot:rst=%s fw=%s`,
> `1.0.0-sim` в собранном образе, и соответствие протоколу на Python-модели
> (`../SonarDebugGUI/protocol_test.py --sim`) — то есть строки, а не живой UART.
> Первое включение имитатора на плате считать отладочным: смотреть в первую
> очередь на целостность длинных строк телеметрии при `debug=1` и на приём
> команд по обоим портам.

## Сборка и прошивка

```bash
pio run                   # сборка
pio run --target upload   # прошивка (WCH-Link, см. platformio.ini)
```

Код проекта собирается со строгими предупреждениями `-Wall -Wextra`
(`build_src_flags` в [platformio.ini](platformio.ini) — именно `build_src_flags`,
чтобы флаги не попали на исходники STM32Cube HAL). Общие библиотеки из
`Software/lib` включают те же флаги у себя в `library.json`. Сборка должна
проходить без единого предупреждения в нашем коде.

## Проверка

Телеметрия и команды — как в основной прошивке (см.
[../FW_SonarMotorDriver/README.md](../FW_SonarMotorDriver/README.md)):

```
boot:rst=por fw=1.0.0-sim  ← первая строка после подачи питания (суффикс -sim)
enc:ok n=16/16 spread=0.000 pos=37.50   ← стартовая позиция модели, дальше «хоуминг» в 0°
cp:0.01,ec:0            ← телеметрия 250 Гц
> mcfg
mode=STEP_DIR run=600 hold=300 microsteps=256 ready=1
> t=90
ok:t=90.00              ← cp плавно едет к 90
> scan=0,90,10,100
ok:scan=0.00,90.00,10.00,100
> stop
ok:stop
> sync=1
ok:sync=1               ← скан шагает по фронту SYNC_IN (PB12)
> sync
sync=1 in=0 out=0 n=0   ← режим, уровни пинов, счётчик фронтов
> hold=0
ok:hold=0               ← удержание снято: модель на паузе, цель сохранена
> hold=1
ok:hold=1               ← движение к той же цели продолжается
> om
om=0                    ← запрос режима выдачи: ответ без префикса ok:
> hold
hold=1                  ← запрос удержания
```

Автотест из основного проекта тоже проходит:
`python ../FW_SonarMotorDriver/tools/test_commands.py COM24`.
