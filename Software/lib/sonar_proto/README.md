# sonar_proto — общий слой командного протокола

Библиотека собирает в одном месте три модуля, которые раньше были продублированы
в `FW_SonarMotorDriver` и `FW_SonarMotorDriver_Sim`:

| Модуль        | Назначение |
|---------------|------------|
| `uart.c/.h`   | Транспорт: USART1 (PA9/PA10) + USART3 (PB10/PB11), кольцевые буферы, DMA/IT. TX дублируется на оба порта, RX объединяется. |
| `line_reader.c/.h` | Выделение одной текстовой строки из кольцевого буфера (`\r`, `\n`, `\r\n`, slow-drain при переполнении). |
| `cmd_parser.c/.h`  | Разбор текстовых команд протокола (`en`, `t=`, `kp=`, `scan=`, `sync=`, `hold=`, …): `Cmd_Parse(const char *line, Cmd_Result *out)` кладёт вид команды (`Cmd_Type`) и её аргументы в `Cmd_Result`. |

Единственный источник правды по протоколу — `Docs/Protocol.md`. Расхождение
между прошивкой и имитатором до выделения библиотеки было реальным: имитатор жил
на более старой копии `uart.c` без исправлений `tx_inflight`, порядка
`ready`/приёма и разбора ошибок в `HAL_UART_ErrorCallback`.

## Подключение

В `platformio.ini` прошивки:

```ini
lib_deps = symlink://../lib/sonar_proto
```

Источник указан явно, каталогом. Короткое имя (`lib_deps = sonar_proto`
в паре с `lib_extra_dirs = ../lib`) опасно: если каталог недоступен — например,
в сборочном образе, куда скопировали только каталог прошивки, — PlatformIO не
падает, а молча тянет одноимённый пакет из публичного реестра и собирает чужой
код. С `symlink://` он в такой ситуации сразу останавливается с ошибкой
«Can not create a symbolic link», а правки в библиотеке видны без копирования
в `.pio/libdeps`.

Заголовки лежат в корне `include/`, поэтому существующие `#include "cmd_parser.h"`
работают без правок.

## Предупреждения компилятора

Библиотека собирается строго: `-Wall -Wextra` заданы в `library.json`
(`build.flags`), а не в `build_flags` прошивки — иначе те же флаги достались бы
исходникам STM32Cube HAL, где предупреждений хватает, а правка чужого
фреймворка в задачи не входит. Своих предупреждений быть не должно: появившееся
разбирают по существу, а не глушат через `-Wno-…`.

## Зависимость от прошивки

`uart.c` включает `board.h` **прошивки** (он попадает в include-путь библиотеки
автоматически, так же как у `lib/tmc2209`). От `board.h` требуются макросы:

* `UART_INSTANCE`, `UART_BAUDRATE`, `UART_TX_PORT/PIN`, `UART_RX_PORT/PIN`;
* `UART3_INSTANCE`, `UART3_BAUDRATE`, `UART3_TX_PORT/PIN`, `UART3_RX_PORT/PIN`,
  `UART3_USE_DMA` (у основной прошивки `0`, у имитатора `1` — каналы DMA1 заняты
  по-разному);
* `UART_TX_RING_SIZE`, `UART_RX_RING_SIZE`, `UART_RX_DMA_SIZE`, `UART_PORT_COUNT`.

Прошивка также обязана перенаправить `HAL_UART_MspInit`/`HAL_UART_MspDeInit`
на `UART_CommandMspInit`/`UART_CommandMspDeInit` для своих экземпляров UART:
MSP общий на всю программу, а UART у прошивки не один (есть ещё порт TMC2209).

## Хостовая проверка парсера

`tools/` — прогон **настоящего** `src/cmd_parser.c` на ПК, без платы и без
кросс-компилятора:

| Файл | Назначение |
|------|------------|
| `tools/cmd_parser_probe.c` | Драйвер: читает строки из stdin, печатает возврат `Cmd_Parse()`, `Cmd_Type` и значимые поля `Cmd_Result`. |
| `tools/run_cmd_parser_probe.py` | Сборка (`gcc -std=c11 -O1 -Wall -Wextra -Werror`) и прогон одной командой. |

```
python tools/run_cmd_parser_probe.py            # таблица по корпусу CORPUS
python tools/run_cmd_parser_probe.py --stdin    # строки из stdin
```

Пример вывода:

```
in="om" rc=1 type=CMD_GET_OUTPUT_MODE
in="omx" rc=1 type=CMD_UNKNOWN
in="mstep 65537" rc=0
in="t=0x10" rc=1 type=CMD_SET_TARGET target=16
```

Зачем это нужно. Привязка протокола к прошивке до сих пор была только
статической: `SonarDebugGUI/tests/test_firmware_commands.py` и
`test_board_constants.py` разбирают `cmd_parser.h/.c` регулярными выражениями,
то есть читают текст, а не исполняют код. Подмену `strcmp(line, "om")` на
`strncmp(line, "om", 2)` такая проверка не видит (регулярка намеренно не
различает две функции), хотя после неё плата отвечает `om=0` на строки `omx` и
`omm`. Зонд же исполняет парсер и ловит это сразу.

Сверка автоматизирована в `SonarDebugGUI/tests/test_cmd_parser_host.py`: тест
собирает зонд, гоняет корпус строк и требует совпадения с моделью прошивки
(`sonar_gui.simulator`) и с `sonar_gui.protocol`. Без компилятора C тест
пропускается; в CI зонд гоняется ещё и отдельным шагом, где gcc есть штатно и
пропуска быть не должно.

Образец подхода — `FW_AS5047P_STM32F103C8/tools/run_filter_model.sh`, где так
же собирается настоящий `src/angle_filter.c`. Раннер здесь написан на Python, а
не на `sh`: его вызывает не только человек, но и юнит-тест, который идёт и на
Windows, где `/bin/sh` может отсутствовать, — а флаги сборки при этом остаются
в одном месте.

Двоичный файл зонда кладётся во временный каталог и удаляется после прогона;
`--out DIR` оставляет его на месте.
